# MapMarker 큰 그림

> 최종 갱신: 2026-11-12 · 단계별 계획은 [PLAN.md](PLAN.md)

## 한 줄 정의

여행 동선, 구간별 이동 방법, 장소 설명과 사진을 담은 **보기 좋은 여행 동선 페이지와 이미지**를 만들고, 다시 보고, 공유하는 앱.

- 핵심 결과물: ① **여행 동선 페이지**(앱 안에서 보는 화면) ② **여행 동선 이미지**(동선이 한눈에 보이는 한 장. 여행 전·중·후 모두 만들고 고친다)
- 로그인하면 **여행 목록**, 여행을 고르면 동선을 따라 지도, 일차를 고르면 그날의 장소와 이동 방법 목록이 나온다.

**해결하려는 문제:** 기존 지도 앱에서는 동선과 장소 포인트를 함께 그리기가 번거롭다.

## 프로젝트 목적

- 실제로 쓰는 서비스를 만든다.
- 포트폴리오와 이직용 경험을 쌓는다. 특히 클라이언트·서버 분리, AWS, 로드밸런싱, AI 연동.
- 원칙: **기술을 쓰려고 서비스를 만들지 않는다.** 서비스를 키우다 필요해질 때 도입하고, 그때마다 `문제 → 측정 → 설계 → 적용 → 검증` 기록을 남긴다.

## 사용 시점

같은 여행(Trip)을 시점에 따라 다른 상태로 쓴다. 편집 기능은 함께 쓴다.

| 시점 | 사용자가 하는 일 |
|---|---|
| 여행 전 (계획) | 갈 만한 곳을 후보로 모으기, 점 찍기, 구간과 이동 수단 정하기, 예정 시각과 메모 남기기, AI로 동선 초안 받기, **계획 동선 이미지 만들기** (예: 동행에게 공유) |
| 여행 중 (진행) | 현재 위치와 다음 장소 확인, 근처 후보 찾기, 방문 체크, 사진 올리기, 지출 적기, **진행 상황 이미지 만들기** |
| 여행 후 (회고) | 사진 붙이기, 실제로 간 대로 수정하기, 동행과 정산하기, **회고 이미지 만들기** |

- **여행 상태는 기간으로 자동 판단한다.** 시작일 전 "전", 기간 중 "중", 종료일 후 "후". 기간이 없으면 "전"이다. "오늘"은 기기의 날짜다.
- 사용자가 직접 바꿀 수도 있고(예: 하루 일찍 출발), 직접 바꾼 상태는 "자동으로 되돌리기" 전까지 유지된다.

## 핵심 기능

- **여행 목록:** 로그인 후 첫 화면. 정사각형 카드가 휴대폰은 한 줄에 2개(태블릿 3~4개)이고, 카드에 상태·제목·기간과 일정이 보인다.
  - 제목은 기본으로 "{지역} {일정} {계절} 여행"(예: "부산 2박 3일 봄 여행", "경주 당일치기 가을 여행")이고 언제든 바꾼다.
  - 길잡이로 **제주 샘플 여행**('제주 3박 4일 가을 여행')이 있다. "샘플" 표시가 붙고 보기만 되며, [실제로 사용하기]로 내 여행에 복사해 고친다. 지우면 그 기기에서는 다시 보이지 않는다.
- **여행 동선 페이지:** 동선을 따라 지도가 나온다. 일차별 또는 여행 전체로 본다.
  - 일차는 선과 마커 색으로 구분하고, 일차 보기는 전날 마지막 장소(보통 숙소)에서 출발한다.
  - 위쪽 칩 두 줄: 첫 줄은 보기(전체, 1일차 …, 후보 목록), 둘째 줄 "함께 보기"는 숙소·후보 장소 켜고 끄기(장소 필터는 이 둘).
- **일차 동선 시트:** 그날의 장소(이름, 예정 시각, 설명, 메모, 사진)와 그 사이 구간(이동 수단)이 차례로 나온다. 세로·좁은 화면은 지도 아래 시트, 가로·넓은 화면은 지도 오른쪽 패널이다.
  - 지도의 포인트나 선을 누르면 그 일차로 들어가 해당 장소·구간을 보여 준다.
  - 장소마다 **네이버 지도 / 구글 맵에서 열기** 칸이 있다(영업시간, 리뷰는 외부 지도에서).
  - 설명은 **사용자가 쓴 내용 + Places 정보**(주소, 영업시간, 평점 등, 2단계)를 나눠 보여 준다.
  - 시트에서 장소를 끌어 순서를 바꾸고, 장소와 구간을 고치고, 장소를 지운다. 새 장소와 다른 일차로 옮기는 장소는 "넣을 자리"(그 일차의 장소 사이)를 고른다.
  - 적어 둔 이동 수단이 사라지게 되면 어느 구간인지 보여 주고 먼저 묻는다.
- **동선 그리기:** 지도에 직접 점을 찍는다. GPS 기록은 나중 단계.
- **후보 장소:** 갈지 정하지 않은 장소를 여행마다 모아 둔다. 지도에는 작은 회색 점과 이름만 보이고 동선(일차·순서·구간)에는 들어가지 않으며, "후보 목록" 보기에서 모아 본다. [동선에 넣기]로 장소가 되고 [후보로 빼기]로 되돌린다. 여행 중에는 일정이 틀어지면 근처 후보로 간다. (1-2 후속, 1-3 전)
- **구간선:** 기본은 직선이고, 구간마다 PPT 곡선처럼 둥글기를 조절한다.
- **이동 수단:** 구간마다 도보, 지하철, 버스, 기차, 차, 비행기, 배 중에서 고르고 아이콘과 선 모양으로 표시한다. 실제 도로 경로는 그리지 않는다.
  - 걸리는 시간은 모든 수단에, 정류장 수는 지하철·버스에 적는다. 갈아타면 이어 적는다(예: 지하철 4정류장 / 지하철 2정류장 + 도보 / 비행기 3시간 20분).
- **시간:** 예정 시각과 실제 시각은 **현지 시간대와 함께** 저장해 해외에서도 현지 시각 그대로 보인다.
- **사진:** 장소마다 1장(없어도 된다). 나중에 여러 장으로 늘 수 있다.
- **지출 기록:** 장소마다 또는 장소 없이 여행에 지출(금액, 통화, 결제 수단, 메모)을 적고 일차·여행 합계를 본다. 외화는 그날 환율이나 직접 넣은 환율로 기준 통화(기본 원)로 바꾸고, 현재 환율로도 본다. (2단계)
- **동행 정산:** 동행(이름만)을 두고 지출마다 낸 사람(동행 또는 공금)과 함께 쓴 사람을 적으면 누가 누구에게 얼마를 보낼지 계산한다. 입력은 여행 주인만, 친구는 공유 링크로 본다. (2단계, 영수증으로 금액 채우기는 7단계 아이디어)
- **이미지 내보내기:** 동선, 이동 수단, 화살표, 장소 이름, 사진이 든 지도 이미지를 **앱에서** 만든다. 언제든 다시 만들고, 항상 최신 여행 데이터로 만든다. 범위(전체/일차별), 비율(1:1, 4:5, 9:16), 사진 포함 같은 옵션이 있다. 앱이 없는 사람에게 공유하는 수단이기도 하다.
- **공유**
  - 앱이 있는 사람: 링크를 누르면 앱에서 여행이 **보기 전용**으로 열린다. 동선·설명·사진은 보이고 메모(작성자의 개인 기록)는 숨긴다.
  - 앱이 없는 사람: 이미지로 공유하고, 링크는 스토어로 보낸다.
  - **공유 끄기 / 링크 새로 발급:** 끄면 기존 링크가 열리지 않고, 새로 발급하면 새 링크만 열린다.
- **내 여행으로 복사:** 공유받은 여행을 내 계정에 복사해 고친다(예: 친구 동선을 내 일정에 맞추기). 원본과 연결되지 않고 "여행 전(계획)"으로 시작한다.
  - **복사하는 것:** 장소(이름, 좌표, 종류, 일차, 순서, 설명, placeId, 예정 시각), 구간(이동 수단, 곡률)
  - **복사하지 않는 것:** 사진, 메모, 방문 체크, 실제 시각
- **오프라인 보기:** 여행 중 화면은 마지막으로 불러온 데이터를 기기에 저장해 인터넷이 끊겨도 보여 준다. (2단계)
- **AI 동선 생성:** 여행지, 계절, 일정(예: 3박4일)을 넣으면 AI가 동선을 만들고, 결과는 편집 가능한 일반 여행이다.
- **로그인:** 네이버, 카카오 소셜 로그인. iOS 출시 때 Apple 로그인을 더한다(App Store 심사 기준). 아이디·비밀번호 로그인은 없고, 받는 정보는 닉네임(선택 동의)뿐이다. 네이버와 카카오로 따로 들어오면 다른 계정이다.
- **회원 탈퇴:** 앱 안에서 계정을 지우면 여행, 사진(S3)을 포함한 데이터를 모두 지운다. 앱 밖에서 삭제를 요청하는 웹 페이지도 둔다(Google Play 정책).
- **삭제와 휴지통:** 지운 여행은 30일 동안 휴지통(여행 목록 `⋮` 메뉴)에 두고 되살리거나 영구 삭제한다. 장소·후보는 바로 지운다. 장소를 지우거나 여행을 영구 삭제하면 S3 사진도 지운다.
- **지도:** 국내는 네이버, 해외는 구글로 **여행 단위 자동 전환**하고, 여행 설정에서 직접 바꿀 수도 있다.

## 기술 스택

| 영역 | 선택 |
|---|---|
| 앱 | Flutter. Android 먼저, iOS는 MVP 이후. **Riverpod**, **go_router**, **gen-l10n**(한국어 먼저) |
| 서버 | **NestJS** (TypeScript) + **Prisma** |
| DB | PostgreSQL (AWS RDS) |
| 파일 | S3 + CloudFront |
| 인프라 | AWS. 단일 EC2로 시작해 ALB와 Auto Scaling으로 확장 |
| 푸시 | FCM (AI 생성 완료 알림 등) |
| 지도 / 장소 | 네이버 지도, 구글 지도 + Google Places |
| 웹 | 정적 페이지, S3 + CloudFront (아래 "웹 페이지") |
| 테스트 | 서버 Jest (단위 + e2e), 앱 `flutter test` (단위 + 위젯) |
| 모바일 웹 서비스 | 지금은 고려하지 않음 |

### 웹 페이지

모바일 웹 서비스는 만들지 않지만, 스토어 정책과 공유 링크 때문에 **단순한 정적 웹 페이지는 꼭 필요하다.**

| 페이지 | 필요한 이유 | 단계 |
|---|---|---|
| 계정 삭제 요청 | Google Play 정책: 앱 밖에서도 삭제를 요청할 수 있어야 한다. 방법 안내 + 요청 경로(문의 메일 또는 간단한 폼) | 1단계 |
| 개인정보처리방침 | 스토어 등록에 공개 URL이 필요하다 | 1단계 |
| 공유 링크 랜딩 | 앱이 없는 사람이 공유 링크를 열면 기기를 판별해 스토어로 보낸다 | 3단계 |
| `assetlinks.json` / `apple-app-site-association` | 공유 링크를 앱에서 여는 App Links / Universal Links 인증 파일 | 3단계 / 6단계 |

## 데이터 구조 (뼈대)

```
User (닉네임?)
├─ SocialAccount (제공자 카카오/네이버, 제공자 사용자 ID)
├─ AuthSession (로그인한 기기 하나: refresh 토큰 해시, 만료)
└─ Trip (여행: 제목, 지역, 일정(몇 박 몇 일), 계절, 기간?(시작일·종료일, 없으면 날짜 미정),
   │      직접 바꾼 상태?(없으면 기간으로 자동), 지도 provider 자동/수동,
   │      생성 출처 직접/AI/복사, 복사 원본 Trip?, 공유 ID?(공유를 끄면 비움),
   │      휴지통에 넣은 시각?, 기준 통화(2단계))
   ├─ Stop (장소: 좌표, 이름, 종류(숙소/음식/관광/기타), 일차, 순서, 설명, 메모, 방문 여부,
   │        예정 시각(일차 + 현지 시:분), 실제 시각(순간), 시간대(예: Europe/Paris),
   │        placeProvider?, placeId?)
   │    └─ Photo (S3 키. 지금은 장소당 1장)
   ├─ Segment (Stop A → Stop B: 이동 수단 목록(수단 + 정류장 수? + 걸리는 시간?),
   │           곡률 k, 타입 일반 / GPS 트랙)
   ├─ Candidate (후보 장소: 좌표, 이름, 종류, 설명, 메모, placeProvider?, placeId?. 일차·순서·사진 없음)
   ├─ Companion (동행: 이름. "나"가 기본, 2단계)
   └─ Expense (지출: 장소?, 날짜, 금액(최소 단위 정수), 통화, 기준 통화 환산 금액, 환율, 환율 출처,
               결제 수단, 메모, 낸 사람(동행 또는 공금), 함께 쓴 동행들, 2단계)
```

## 주요 결정과 이유

화면 동작의 세부(크기, 거리, 어느 탭에서 무엇이 뜨는지)와 이유는 앱 코드 주석과 테스트에 있다. 여기에는 바꾸려면 기획부터 봐야 하는 결정만 둔다. "(실기기)"는 실기기에서 써 보고 정한 것이다.

### 데이터와 시간

| 결정 | 이유 |
|---|---|
| ID는 앱이 UUID v7로 만든다. 구간 ID는 서버가 UUID v7로, 공유 ID는 서버가 무작위로 만든다 | 앱이 만든 ID는 서버 ID로 바꿔 끼울 필요가 없고 같은 요청을 다시 보내도 중복되지 않는다. v7은 시각 순서라 인덱스에 유리하다. 구간은 장소 순서에서 따라 나와서 서버가 장소를 넣고 옮기고 지울 때 앱과 같은 규칙으로 만들고 지우며, 응답에 그 여행의 장소·구간 전체를 담아 앱은 받은 값으로 바꾼다. 공유 ID는 추측할 수 없어야 한다 |
| 여행 상태(전/중/후)는 앱이 기기의 오늘 날짜와 기간으로 계산하고, 서버에는 직접 바꾼 상태만 저장한다 | 저장한 자동 상태는 날이 지나면 낡는다. 서버는 기기 시간대를 몰라 날짜가 하루 어긋날 수 있다(UTC면 한국 오전 9시 전은 전날) |
| 기간은 시간대 없는 날짜, 예정 시각은 일차 + 현지 시:분, 실제 시각은 순간(UTC)과 현지 시간대로 둔다 | 시간대가 없으면 해외 여행의 시각이 틀어진다. 예정 시각에 날짜가 없어야 기간 없는 여행에도 넣고, 날짜를 옮기거나 복사해도 맞는다(날짜 = 시작일 + (일차 − 1)) |
| 장소는 (일차, 순서)로 늘어선 한 줄이고, 구간은 이웃한 두 장소 사이에 자동으로 만들고 지운다. 일차를 넘어서도 잇는다. 이웃이 바뀐 구간의 이동 수단은 사라진다 | 선을 따로 잇지 않아도 되고 "구간 = 선"으로 단순하다. 전날 숙소 → 다음 날 첫 장소, 야간 비행기·배도 구간이 된다. 이웃이 바뀌면 경로가 바뀐 것이다 |
| 이동 수단은 구간마다 여러 토막(수단 + 정류장 수 + 걸리는 시간)이고, 서버는 jsonb 칼럼 하나에 담아 모양은 API가 검사한다 | 실제 이동은 "지하철 2정류장 + 도보"처럼 갈아타는 일이 많다. 늘 통째로 읽고 바꿔서 테이블을 나눌 이유가 없다. 안을 질의할 일이 생기면 그때 옮긴다 |
| 곡선은 구간마다 곡률 `k`(0이면 직선, 부호가 방향, −1~1)만 저장하고, 앱이 메르카토르 좌표에서 2차 베지어로 그린다 | 저장이 단순하고 지도 종류와 관계없이 똑같이 그려진다. 위도·경도로 계산하면 찌그러진다. 날짜변경선을 넘는 구간은 따로 처리한다 |
| Segment 타입은 "일반 / GPS 트랙"이다 | 직선·곡선은 `k`로 구분되고, 타입은 그리는 방식이 다른 GPS 트랙만 가른다 |
| 장소 종류는 숙소·음식·관광·기타 4개이고 숙소만 동선 규칙이 있다 | 적어야 고를 때 헷갈리지 않고, 늘리기는 쉽고 나누기는 어렵다. 교통(공항·역)은 이동 수단 아이콘으로 드러난다 |
| 숙소는 그날 밤 묵는 곳을 그 일차 마지막 장소로 넣는다. 한 여행에 숙소가 여러 곳일 수 있다 | 밤마다 한 번만 넣어도 "숙소 > 장소들 > 숙소"로 하루가 보이고, 숙소를 옮기는 날도 그대로 그려진다 |

### 동선 화면

| 결정 | 이유 |
|---|---|
| 일차는 선과 마커의 **색**으로, 이동 수단은 선 **모양**과 아이콘으로 구분한다 | 전체 보기에서 어느 날의 동선인지 한눈에 보이는 것이 가장 중요하다. 한 채널(색)에 두 정보를 담으면 섞인다 |
| 선 모양은 3갈래(실선: 차·버스·지하철·기차, 둥근 점선: 도보, 긴 파선: 비행기·배)이고 정확한 수단은 아이콘이 맡는다. 미정 구간은 실선에 아이콘이 없다 | 7개를 모두 다르게 그리면 작은 화면에서 구분되지 않는다. 미정은 정상 상태라 흐리게 그리지 않는다 |
| 갈아타는 구간은 대표 수단 하나(비행기 > 배 > 기차 > 지하철 > 버스 > 차 > 도보)로 선 모양과 아이콘을 정하고, 모든 토막은 시트에서 보여 준다 | 아이콘이 여럿이면 어지럽고, 갈아탄 위치를 몰라 선을 나눌 수 없다. 걸리는 시간은 비울 수 있어 수단 순서로 고른다 |
| 진행 방향 화살표는 저장하지 않고 구간 가운데에, 수단 아이콘은 1/4 지점(출발 쪽)에 그린다. 선이 화면에서 짧으면 숨긴다 | 방향은 이미 구간에 있다. 끝점은 도착 마커에 가린다. 1/4 지점이면 마커·아이콘·화살표가 고르게 떨어지고 "지하철을 타고 떠난다"로 읽힌다 |
| 곡률은 지도에서 구간 가운데 핸들(화살표가 든 원)을 끌어 고친다. 핸들은 시트에서 그 구간 줄을 직접 고른 때만 뜨고, 직선 가까이 끌면 직선에 붙는다 | PPT 곡선처럼 지도 위 모양을 보며 맞추는 쪽이 "보기 좋은 동선 이미지"라는 목적에 맞는다 |
| 일차 보기는 앞 일차의 마지막 장소에서 출발한다(숙소가 아니어도: 공항, 야간 이동) | 일차를 넘는 구간이 다음 날 보기에 보여야 이동 수단을 적고 고친다. 같은 장소를 다음 날 또 넣게 하면 길이 0인 구간이 생기고 야간 이동을 담지 못한다 |
| 같은 자리에 여러 번 넣은 장소는 지도에서 마커 하나로 합친다 | 연박 숙소, 같은 공항으로 시작하고 끝나는 여행이 흔하다. 겹치면 아래 마커를 누를 수 없다 |
| 장소 필터는 숙소와 후보 장소 켜기/끄기 둘만 둔다 | 같은 숙소에 여러 날 묵으면 드나드는 선이 겹쳐 어지럽고, 공유 이미지에서 머무는 곳을 감추고 싶을 수 있다(개인정보). 후보는 동선만 보고 싶을 때 끈다 |
| 위쪽 칩은 두 줄이다. 첫 줄은 하나만 고르는 보기(전체, 1일차 …, 후보 목록), 둘째 줄은 "함께 보기" 뒤에 켜고 끄는 필터(숙소, 후보)이고 칩과 누르는 영역을 작게 한다 | 한 줄에 "후보"(보기)와 "후보 보기"(필터)가 나란히 있어 헷갈렸다(실기기). 필터는 가끔 바꿔서 작게 해 지도를 덜 가린다. 숙소 필터는 목록에서도 숨겨서 "지도에 표시"가 아니라 "함께 보기"다 |
| 숙소를 끄면 숙소에 닿는 구간은 빠지고, 낮에 들른 숙소의 앞뒤는 흐린 "숙소를 거침" 선(가는 파선, 누를 수 없음)으로 잇는다. 하루가 끝나는 밤 숙소는 잇지 않는다 | 끊으면 하루 동선이 끊겨 보인다. 숙소 자리를 거치면 숨긴 위치가 드러나고, 보통 선이면 가지 않은 길이 공유 이미지에 남는다 |
| 숙소를 끈 보기에서는 끌어 옮기기를 막고 [숙소 켜기]로 안내한다. 필터는 앱이 몰래 켜지 않는다 | 숨긴 숙소가 사이에 섞여 끌어 놓은 자리가 분명하지 않고, 보이지 않던 구간의 이동 수단이 지워진다 |
| 지도 전환은 화면이 아니라 **여행 단위**다. Stop이 모두 국내면 네이버, 하나라도 해외면 구글 | 지도를 움직일 때마다 바뀌면 깜빡이고 어색하다 |

### 일차 동선 시트와 편집

| 결정 | 이유 |
|---|---|
| 장소 상세는 장소 하나의 화면이 아니라 일차 동선 시트(목록)로 보여 준다 | 핵심은 장소 하나보다 "그날 어떻게 움직이나"다. 장소와 이동 방법이 함께 보이고, 순서도 목록에서 끈다 |
| 시트는 깔끔하게 둔다. 연필(고치기)·손잡이(순서)는 시트에서 직접 누른 줄에만 뜨고, 장소 지우기는 장소 입력 화면 안에 둔다 | 지도에서 눌러 연 시트는 보려고 연 것이다. 버튼이 늘 보이면 어지럽고 실수로 지우거나 옮기기 쉽다 |
| 가로이고 폭이 600dp 이상이면 시트 대신 지도 오른쪽 패널이다 | 가로 화면은 세로가 짧아 시트를 올리면 지도와 목록이 모두 납작해진다. 오른쪽이면 왼쪽 아래 지도 로고도 가리지 않는다 |
| 새 장소와 다른 일차로 옮기는 장소는 "넣을 자리" 칸에서 그 일차의 장소 사이를 고른다. 기본은 맨 뒤(마지막이 숙소면 숙소 앞)이고, 그날 밤 숙소 뒤에는 숙소만 넣는다 | 기본 자리에 들어가 엉뚱한 구간의 이동 수단이 지워지는 일을 막는다. 밤 숙소 뒤에 장소를 넣으면 그 숙소가 낮에 들른 곳이 되어 다음 날 출발이 바뀐다(실기기). 가까운 자리에 자동으로 넣지 않는다(틀리면 이유를 알 수 없다) |
| 적어 둔 이동 수단이 사라지게 되면 그 구간을 일차와 함께("2일차 용두암 → 동문시장") 먼저 보여 준다. 입력 화면은 "넣을 자리" 칸 아래에 미리 보여 주고, 끌기와 연박은 대화상자로 묻는다 | 모르고 넣거나 옮기면 적어 둔 정보를 잃는다. 끼어드는 자리의 구간도 사라져서 어느 구간인지 보여야 판단한다. 입력 화면은 고르면서 보니 저장할 때 다시 묻지 않는다 |
| 예정 시각은 아래 시트의 휠(오전/오후 · 시 · 분)로 5분 단위로 고른다. 5분 단위가 아닌 예전 시각은 가까운 5분에서 시작하고 [확인]을 눌러야 바뀐다 | 휴대폰 알람과 같은 휠이 익숙하고, 계획에는 5분이면 충분해 덜 굴린다. Flutter 기본 위젯이라 iOS도 된다 |

### 후보 장소

| 결정 | 이유 |
|---|---|
| 후보는 장소(Stop)와 따로 된 모델이다. 일차·순서·사진이 없고 넣은 순서로 보여 준다 | 장소는 일차·순서가 필수이고 동선 규칙(순서 다시 매기기, 구간 잇기)과 DB 제약이 이를 전제한다. "일차 없는 장소"로 넣으면 그 규칙을 모두 고쳐야 한다 |
| [동선에 넣기]와 [후보로 빼기]는 서버가 한 번에 바꾸고 같은 ID를 쓴다 | 둘로 나눠 보내면 중간에 실패할 때 장소가 사라지거나 두 번 생긴다. 같은 ID라 앱이 선택과 위치를 따라가기 쉽다 |
| 지도: "함께 보기"의 "후보"(기본 켜짐)로 전체·일차 보기 모두에 모든 후보를 흰 바탕·회색 테두리의 작은 점과 회색 이름으로 보인다. 일차 색 없이 동선 마커 아래에 그리고, 카메라 맞춤에 넣지 않는다 | 동선을 보며 고르려고 모으니 기본으로 보인다. 동선보다 눈에 덜 띄어야 하고, 카메라가 후보까지 넓어지면 동선이 작아진다 |
| 필터가 꺼진 보기에서 저장하면 "후보로 저장했습니다." [후보 켜기]만 알린다(숙소도 같다). 앱이 몰래 켜지 않는다 | 안 보이면 저장이 안 된 줄 안다. 몰래 켜면 사용자가 끈 설정이 사라진다. 긴 설명은 거슬린다(실기기) |
| 넣기: 지도를 누르면 뜨는 카드에서 [후보로 저장] / [동선에 넣기]. 후보 입력 화면은 이름·종류·설명·메모만 받는다 | 일차·자리·예정 시각은 동선에 넣을 때 정한다. 묻는 것이 적어야 빨리 모은다 |
| 목록: 보기 칩 줄 끝의 "후보 목록" 보기. 지도는 동선을 흐리게 깔고 후보에 카메라를 맞추며, 시트·패널은 넣은 순서 목록이다. 줄을 누르면 설명·메모·[동선에 넣기]·연필이 펼쳐진다. 다른 보기에서 후보 점을 누르면 이 보기의 그 줄로 온다 | 일차 시트와 같은 자리, 같은 펼침이라 새로 배울 것이 없다. 흐린 동선 위에 보여야 어디에 넣을지 판단한다 |
| [동선에 넣기]는 후보 값을 채운 장소 입력 화면(일차·넣을 자리·예정 시각, 지워질 이동 수단 미리 알림)을 열고, 넣으면 그 일차로 가서 보여 준다 | 장소 넣기와 같은 화면이라 자리 고르기와 이동 수단 경고를 그대로 쓴다 |
| [후보로 빼기]는 장소 입력 화면의 "장소 지우기" 위에 있다(출발 장소에는 없다). 이동 수단을 적은 구간이나 예정 시각이 사라질 때만 묻고, 고친 이름·종류·설명·메모는 먼저 저장한다. 뺀 뒤 보기는 그대로 두고 [후보 목록] 스낵바만 준다 | 잃는 것이 없으면 묻는 것이 번거롭다. 고친 값은 후보에 남는 값이라 버리면 놀란다. 뺀 뒤에는 그 일차를 이어서 고칠 때가 많다 |
| 후보는 여행을 따라간다: 휴지통 여행의 후보는 없는 것(404), 되살리면 함께, 영구·예약 삭제와 회원 탈퇴 때 함께 지운다. 후보 하나는 확인 창 뒤 바로 지운다 | 휴지통 대상은 여행만이라는 결정과 같다. 후보는 장소보다 가벼운 메모다 |
| 제주 샘플에 동선에 없는 후보 3곳을 넣고 [실제로 사용하기] 때 함께 복사한다 | 처음 쓰는 사람이 후보가 무엇인지 보고 안다 |
| 사진(1-3)·내보내기(1-5) 전에 만든다 | 사진이 장소에 붙고 내보내기가 장소를 그리기 전에 모델을 정해야 고칠 곳이 적다 |
| 내보내기 이미지에는 기본으로 넣지 않는다. 공유 화면과 복사에 넣을지는 3단계에서 정한다(제안: 공유에 보이고 복사에 넣는다) | 이미지는 정해진 동선을 보여 주는 결과물이다. 후보는 계획 정보라 공유받은 사람에게도 쓸모가 있다 |

### 지출 기록과 동행 정산

| 결정 | 이유 |
|---|---|
| 2단계에서 해외(2-1)·오프라인(2-2) 뒤에 만든다(2-5 지출, 2-6 정산). 영수증 인식은 7단계 아이디어다 | 통화·환율은 해외와 함께 설계하고, 해외에서는 인터넷 없이 적는 일이 많아 오프라인 저장이 먼저다. 영수증 인식은 사진(1-3)과 AI(2-3) 위의 편의 기능이다 |

| 동행은 계정이 아니라 이름 목록이다. 입력은 여행 주인만 하고 친구는 공유 링크로 본다 | 공동 편집을 하지 않는다는 결정(멤버·권한·동시 수정)을 지키며 정산을 한다. 각자 입력하게 하려면 공동 편집 결정부터 다시 본다 |
| 공유 화면에 지출·정산을 보일지는 3단계에서 정한다(제안: 기본은 숨기고 주인이 켠다). 복사할 때 지출과 동행은 넣지 않는다 | 지출은 사진·메모처럼 개인 기록이다. 정산을 보여 주려면 주인이 고를 수 있어야 한다 |

### 사진, 이미지, 공유

| 휴지통의 여행은 휴지통 API 말고는 없는 여행이다(공유 링크 포함). 공유 ID는 지우지 않아 되살리면 예전 링크가 다시 열리고, 넣고 되살릴 때 고친 시각은 바꾸지 않는다 | 되살리면 지우기 전과 똑같아야 덜 헷갈린다(목록의 원래 자리, 링크). 링크를 막으려면 공유 끄기가 있다 |
| 보관 기간(30일)은 서버가 정한다. 서버가 한 시간마다 기간이 끝난 여행을 지우고, 휴지통 목록에 지울 시각을 준다. 앱은 그 시각으로 남은 날을 보여 준다(앱에는 안내 문구의 "30일"만 있다) | 기간을 바꿔도 앱 업데이트 없이 맞는다. 같은 조건으로 지워 여러 번 돌려도 결과가 같아 서버가 여러 대(4단계)여도 된다 |
| 제주 샘플은 휴지통에 넣지 않고 기기에서 숨긴다. 설정 화면(1-6)에 "샘플 여행 다시 보기"를 둔다 | 샘플은 앱에 담긴 안내라 서버에 없고 숨김은 기기 단위다. 계정 단위 휴지통과 섞으면 기기마다 휴지통이 달라 보이고 기기에 30일 삭제를 따로 만들어야 한다 |
| 외부 지도 연결은 이름과 좌표로 검색 링크를 만든다(네이버: `https://map.naver.com/p/search/{이름}?c={경도},{위도},15,0,0,0,dh`). placeId가 있으면 함께 쓴다 | MVP에는 Places가 없어 이름과 좌표만 있다. 네이버 공개 API는 영업시간을 주지 않아 외부 지도에서 본다 |
| 장소 설명은 사용자 작성 내용과 Places 정보를 나눠 보여 준다 | 개인 기록과 객관 정보를 구분한다. Places 정보는 placeId로 조회해 2단계부터다 |
| 공유받은 여행은 보기만 하고, 고치려면 내 여행으로 복사한다 | 공동 편집은 멤버, 권한, 동시 수정 충돌 처리가 필요해 범위가 크다. 복사로 같은 목적을 훨씬 단순하게 이룬다 |
| 공유 화면에서 메모는 숨기고, 복사할 때 사진과 메모는 뺀다. 예정 시각은 복사한다 | 사진과 메모는 작성자의 개인 기록이다. 사진 파일을 같이 쓰면 원본을 지울 때 복사본이 깨지고, 복제하면 S3 비용이 든다. 시간 순서는 그 자체가 동선 정보다 |
| 공유를 끄거나 링크를 새로 발급할 수 있다 | 링크는 한 번 퍼지면 회수할 수 없어 막을 수단이 필요하다 |

### 로그인과 계정

| 결정 | 이유 |
|---|---|
| 앱이 카카오·네이버 SDK로 받은 토큰을 서버가 검증한다. 카카오는 **id_token**(OpenID Connect)의 서명(카카오 공개키)·발급자·대상 앱(`aud`)·만료를, 네이버는 **access token**으로 프로필 API를 불러 확인한다 | 앱이 보낸 사용자 ID는 믿을 수 없다. id_token은 로그인마다 카카오를 부르지 않고, Apple·구글도 같은 방식이라 검증 코드를 다시 쓴다. 네이버 Flutter SDK는 id_token을 주지 않는다. 네이버 사용자 ID는 앱마다 달라 다른 앱의 토큰으로 우리 계정에 닿지 못한다 |
| 검증 뒤 서버가 access 토큰(JWT, 15분)과 refresh 토큰(30일)을 준다. refresh 토큰은 무작위 문자열이고 DB에는 해시만 둔다. 쓸 때마다 바꾸고, 이미 바뀐 예전 토큰이 다시 오면 탈취로 보고 그 기기의 로그인을 끊는다 | 제공자 토큰에 매번 기대지 않고 API를 같은 방식으로 지킨다. access 토큰은 DB를 안 봐서 서버를 늘려도 그대로고, refresh 토큰은 DB에 있어야 로그아웃·탈퇴·탈취 때 끊는다 |
| 같은 사람이 카카오와 네이버로 따로 들어와도 계정을 잇지 않는다 | 믿고 이을 공통 값이 없다(이메일을 받지 않는다). 이메일로 합치면 확인되지 않은 이메일로 남의 계정을 가로챌 수 있다. 사용자 하나에 소셜 계정 여럿을 둘 수 있게 만들어 나중에 직접 잇기는 더할 수 있다 |
| 받는 정보는 닉네임(선택 동의, 가입 때만)뿐이다. 이메일·이름·사진·전화번호와 제공자 토큰은 저장하지 않는다 | 개인정보가 적으면 처리방침과 탈퇴가 단순하다. 서버는 제공자 API를 부를 일이 없다. 탈퇴 때 제공자 연결 끊기는 앱이 SDK로 한다 |
| 제공자에 닿지 못하면 401이 아니라 503이다 | 앱이 "다시 로그인"과 "잠시 후 다시"를 나눠 보여 준다 |
| 네이버 로그인의 Client Secret은 앱(APK)에 들어간다(비밀값을 앱에 두지 않는 규칙의 예외). 커밋하지 않는 `android/local.properties`에서 빌드 때 매니페스트로만 넣고, Dart 코드와 `.env`에는 두지 않는다. SDK 로그는 끈다 | 네이버 로그인 SDK가 초기화에 Secret을 요구한다. Secret 없는 방식(PKCE)은 토큰 요청이 `invalid_client`로 거절됐다. `.env`는 Dart까지 가고, SDK 로그를 켜면 설정값이 logcat에 남는다. 서버는 Secret 없이 access token만 검증해서, 꺼낸 Secret으로 우리 계정에 닿을 수 없다 |

### 기술과 인프라

| 결정 | 이유 |
|---|---|
| 서버는 NestJS다 | 인증, 검증, 횟수 제한, 큐, Swagger가 공식 모듈로 있고 구조가 정해져 있어 유지보수하기 쉽다 |
| 상태 관리는 Riverpod을 코드 생성 없이 쓴다 | 서버 데이터의 로딩·에러 상태를 기본으로 지원하고, 저장소·지도 구현을 바꿔 끼우기 쉽다(테스트의 메모리 저장소·가짜 지도). 모델이 적은 지금은 코드 생성 부담이 더 크다 |
| 라우팅은 go_router다 | 3단계 공유 링크(딥링크)를 경로 표로 연결하고, 로그인 후 원래 화면으로 돌려보내기를 한 곳(redirect)에서 한다 |
| 테스트는 각 진영의 기본 도구(Jest, `flutter test`)이고 단계별 완료 기준에 넣는다 | 가장 널리 쓰여 자료가 많고 설정이 적다 |
| 처음부터 stateless다(JWT 인증, 파일은 S3) | 서버가 여러 대가 돼도 코드를 고치지 않는다 |
| 로드밸런서는 **부하 테스트로 병목을 확인한 뒤** 넣는다 | 근거와 수치가 있는 개선 스토리가 된다 |
| iOS는 MVP 이후, 맥이 있는 친구에게 부탁한다 | iOS 빌드와 디버깅에는 Xcode(macOS)가 필요하다 |

## 알아 둘 제약

- 네이버 지도는 해외 상세도가 낮고, 네이버 장소 검색은 사실상 국내 전용이다.
- 네이버 Directions API는 자동차 경로만 준다. 그래서 직선·곡선으로 그린다.
- Firebase Dynamic Links는 2025년에 끝났다. 앱 링크는 App Links / Universal Links로 직접 만든다.
- 스토어 출시에 필요한 것
  - **개인정보처리방침:** 위치와 사진을 다뤄 필수다. 수집 항목, 이용 목적, 보관 기간, 삭제 방법을 조사해 쓴다.
  - **계정 삭제:** Google Play는 계정을 만드는 앱에 앱 안 삭제와 웹 삭제 요청 경로를 요구한다.
  - **iOS:** Apple 개발자 계정(연 $99, 본인 명의). 소셜 로그인이 있으면 Apple 로그인도 필요하다.
- AWS 비용: ALB는 트래픽이 없어도 기본 요금이 나오고, NAT Gateway는 비싸다. Budget 알림을 처음부터 켠다.
