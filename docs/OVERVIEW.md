# MapMarker 큰 그림

> 최종 갱신: 2026-11-20 · 단계별 계획은 [PLAN.md](PLAN.md)

## 한 줄 정의

여행 동선, 구간별 이동 방법, 장소 설명과 사진을 담은 **보기 좋은 여행 동선 페이지와 이미지**를 만들고, 다시 보고, 공유하는 앱.

- 핵심 결과물: ① **여행 동선 페이지**(앱 안 화면) ② **여행 동선 이미지**(동선이 한눈에 보이는 한 장, 여행 전·중·후 언제든 만든다)
- 로그인하면 여행 목록, 여행을 고르면 동선을 따라 지도, 일차를 고르면 그날의 장소와 이동 방법 목록이 나온다.
- **해결하려는 문제:** 기존 지도 앱에서는 동선과 장소 포인트를 함께 그리기가 번거롭다.

## 프로젝트 목적

- 실제로 쓰는 서비스를 만들고, 포트폴리오와 이직용 경험(클라이언트·서버 분리, AWS, 로드밸런싱, AI 연동)을 쌓는다.
- 원칙: **기술을 쓰려고 서비스를 만들지 않는다.** 필요해질 때 도입하고 `문제 → 측정 → 설계 → 적용 → 검증`을 기록한다.

## 사용 시점

같은 여행(Trip)을 시점에 따라 다른 상태로 쓰고, 편집 기능은 함께 쓴다.

| 시점 | 사용자가 하는 일 |
|---|---|
| 여행 전 (계획) | 후보 모으기, 점 찍기, 구간과 이동 수단, 예정 시각과 메모, AI 동선 초안, **계획 동선 이미지** |
| 여행 중 (진행) | 현재 위치, 근처 후보, 방문 체크, 사진, 지출, **진행 상황 이미지** |
| 여행 후 (회고) | 사진 붙이기, 실제로 간 대로 고치기, 동행 정산, **회고 이미지** |

- **상태는 기간으로 자동 판단한다**(시작일 전 "전", 기간 중 "중", 종료일 후 "후", 기간이 없으면 "전". 오늘은 기기 날짜). 직접 바꾼 상태는 "자동으로 되돌리기" 전까지 유지된다.

## 핵심 기능

- **여행 목록:** 첫 화면. 정사각형 카드에 상태·제목·기간과 일정. 기본 제목은 "{지역} {일정} {계절} 여행"이고 언제든 바꾼다. 보기만 되는 **제주 샘플 여행**을 [실제로 사용하기]로 내 여행에 복사한다.
- **여행 동선 페이지:** 일차별 또는 전체로 지도를 본다. 일차는 선과 마커 색으로 구분하고, 일차 보기는 전날 마지막 장소에서 출발한다. 위쪽 칩 첫 줄은 보기(전체, 1일차 …, 후보 목록), 둘째 줄 "함께 보기"는 숙소·후보 켜고 끄기이고, 두 줄을 요약 알약 하나로 접을 수 있다.
- **일차 동선 시트:** 그날의 장소(이름, 예정 시각, 설명, 메모, 사진)와 구간(이동 수단)이 차례로 나온다. 세로 화면은 지도 아래 시트, 가로·넓은 화면은 오른쪽 패널이다.
  - 지도의 포인트나 선을 누르면 해당 줄로 간다. 펼친 줄에서 **네이버 지도 / 구글 맵에서 열기**(영업시간, 리뷰는 외부 지도에서).
  - 끌어 순서를 바꾸고, 장소와 구간을 고치고 지운다. 장소 사이 ⊕로 그 자리에 넣고, 그 밖에는 일차의 기본 자리에 들어간다.
- **장소 찾기:** 지도 앱에서 복사한 주소나 건물명 한 줄로 찾아 그 위치에 장소·후보를 넣는다(이름은 사용자가 쓴다). 국내만(행안부 도로명주소 API). 주소로 못 찾는 곳(해변, 오름)은 지도에 직접 점을 찍는다.
- **후보 장소:** 갈지 정하지 않은 장소를 여행마다 모은다. 동선에 들어가지 않고 지도에 작게 보이며, "후보 목록" 보기에서 모아 본다. [동선에 넣기]와 [후보로 빼기]로 오간다.
- **구간과 이동 수단:** 기본은 직선이고 구간마다 둥글기를 조절한다. 수단(도보, 지하철, 버스, 기차, 차, 비행기, 배)은 아이콘과 선 모양으로 보이고 실제 도로 경로는 그리지 않는다. 걸리는 시간, 정류장 수, 갈아타기를 적는다.
- **여행 중:** [내 위치]로 현재 위치를 보고 후보를 가까운 순으로 본다. 장소 줄의 동그라미로 방문을 기록하고 실제 방문 시각을 남긴다. 기간 중에는 오늘 일차로 열린다.
- **시간:** 예정·실제 시각은 **현지 시간대와 함께** 저장해 해외에서도 현지 시각 그대로 보인다.
- **사진:** 장소마다 1장(없어도 된다, 나중에 여러 장). 지도와 이미지에 보일 정사각형 부분을 사용자가 고른다.
- **이미지 내보내기:** 동선, 이동 수단, 화살표, 장소 이름, 사진이 든 지도 이미지를 **앱에서** 늘 최신 데이터로 만든다. 범위(전체/일차), 비율(1:1, 4:5, 9:16), 사진 포함 같은 옵션. 앱이 없는 사람에게 공유하는 수단이기도 하다.
- **공유:** 앱이 있으면 링크로 **보기 전용**으로 열린다(메모는 숨김). 없으면 이미지로 공유하고 링크는 스토어로 보낸다. 공유를 끄거나 링크를 새로 발급한다.
- **내 여행으로 복사:** 공유받은 여행을 복사해 고친다. 원본과 연결되지 않고 "여행 전"으로 시작한다. 장소(이름, 좌표, 종류, 일차, 순서, 설명, placeId, 예정 시각)와 구간(이동 수단, 곡률)만 복사하고 사진, 메모, 방문, 실제 시각은 뺀다.
- **지출 기록과 동행 정산 (2단계):** 장소나 여행에 지출(금액, 통화, 결제 수단, 메모)을 적고 합계를 본다. 외화는 그날 환율이나 직접 넣은 환율로 기준 통화(기본 원)로 바꾼다. 동행(이름만)마다 낸 사람과 함께 쓴 사람을 적으면 누가 누구에게 얼마를 보낼지 계산한다.
- **오프라인 보기 (2단계):** 마지막으로 불러온 데이터를 기기에 저장해 끊겨도 여행 중 화면을 본다.
- **AI 동선 생성:** 여행지, 계절, 일정을 넣으면 AI가 편집 가능한 일반 여행을 만든다.
- **로그인과 탈퇴:** 네이버, 카카오 소셜 로그인(iOS 출시 때 Apple). 받는 정보는 닉네임(선택)뿐이다. 앱 안에서 탈퇴하면 사진(S3)까지 모두 지우고, 앱 밖 삭제 요청 웹 페이지도 둔다(Google Play 정책).
- **삭제와 휴지통:** 지운 여행은 30일 동안 휴지통에 두고 되살리거나 영구 삭제한다. 장소·후보는 바로 지운다.
- **지도:** 국내는 네이버, 해외는 구글로 **여행 단위 자동 전환**하고 여행 설정에서 바꿀 수 있다.

## 데이터 구조 (뼈대)

```
User (닉네임?)
├─ SocialAccount (제공자 카카오/네이버, 제공자 사용자 ID)
├─ AuthSession (로그인한 기기 하나: refresh 토큰 해시, 만료)
└─ Trip (제목, 지역, 일정(몇 박 몇 일), 계절, 기간?(없으면 날짜 미정), 직접 바꾼 상태?,
   │      지도 provider 자동/수동, 생성 출처 직접/AI/복사, 복사 원본 Trip?, 공유 ID?,
   │      휴지통에 넣은 시각?, 기준 통화(2단계))
   ├─ Stop (좌표, 주소, 이름, 종류(숙소/음식/관광/기타), 일차, 순서, 설명, 메모, 방문 여부,
   │        예정 시각(일차 + 현지 시:분), 실제 시각(순간), 시간대, placeProvider?, placeId?)
   │    └─ Photo (원본 S3 키(썸네일 키는 여기서 만든다), 지금은 장소당 1장)
   ├─ Segment (Stop A → Stop B: 이동 수단 목록(수단 + 정류장 수? + 걸리는 시간?), 곡률 k, 타입 일반/GPS 트랙)
   ├─ Candidate (좌표, 주소, 이름, 종류, 설명, 메모, placeProvider?, placeId?. 일차·순서·사진 없음)
   ├─ Companion (동행 이름, "나"가 기본, 2단계)
   └─ Expense (장소?, 날짜, 금액(최소 단위 정수), 통화, 기준 통화 환산 금액, 환율, 환율 출처,
               결제 수단, 메모, 낸 사람(동행 또는 공금), 함께 쓴 동행들, 2단계)
```

## 주요 결정과 이유

바꾸려면 기획부터 봐야 하는 결정만 둔다. 화면 동작의 세부는 앱 코드 주석과 테스트에, 서버 세부는 서버 `CLAUDE.md`에 있다. "(실기기)"는 실기기에서 써 보고 정한 것이다.

### 데이터와 시간

| 결정 | 이유 |
|---|---|
| ID는 앱이 UUID v7로 만든다. 구간 ID는 서버가 v7로, 공유 ID는 서버가 무작위로 만든다 | 앱 ID는 다시 보내도 중복되지 않고 v7은 시각 순서라 인덱스에 유리하다. 구간은 장소 순서에서 나와서 서버가 앱과 같은 규칙으로 만든다. 공유 ID는 추측할 수 없어야 한다 |
| 여행 상태(전/중/후)는 앱이 기기 날짜로 계산하고, 서버에는 직접 바꾼 상태만 저장한다 | 저장한 자동 상태는 날이 지나면 낡고, 서버는 기기 시간대를 몰라 하루 어긋날 수 있다 |
| 기간은 시간대 없는 날짜, 예정 시각은 일차 + 현지 시:분, 실제 시각은 순간(UTC)과 현지 시간대다 | 시간대가 없으면 해외 시각이 틀어진다. 예정 시각에 날짜가 없어야 기간 없는 여행에도 넣고 날짜를 옮기거나 복사해도 맞는다 |
| 장소는 (일차, 순서)로 늘어선 한 줄이고, 구간은 이웃한 두 장소 사이에 자동으로 생기고 일차를 넘어서도 잇는다. 이웃이 바뀐 구간의 이동 수단은 사라진다 | "구간 = 선"으로 단순하고, 전날 숙소 → 다음 날 첫 장소, 야간 비행기·배도 구간이 된다. 이웃이 바뀌면 경로가 바뀐 것이다 |
| 이동 수단은 구간마다 여러 토막(수단 + 정류장 수 + 걸리는 시간)이고 서버는 jsonb 칼럼 하나에 담는다 | 갈아타는 일이 많다. 늘 통째로 읽고 바꿔서 테이블을 나눌 이유가 없다 |
| 곡선은 구간마다 곡률 `k`(0이면 직선, 부호가 방향, −1~1)만 저장하고 앱이 메르카토르 좌표에서 2차 베지어로 그린다 | 지도 종류와 관계없이 똑같이 그려진다(위경도로 계산하면 찌그러진다) |
| 장소와 후보에는 좌표, 주소, 이름, 종류, 설명, 메모를 둔다. 주소는 검색에서 고르면 채워지고 사용자가 고친다. 글자만 고치면 좌표는 그대로다 | 방문할 곳을 알아보는 데 필요한 것만 둔다(사용자 결정). 좌표는 그리는 값이라 주소와 따로 둔다 |
| 장소 종류는 숙소·음식·관광·기타 4개이고 숙소만 동선 규칙이 있다 | 적어야 고르기 쉽고, 늘리기는 쉽고 나누기는 어렵다. 교통은 이동 수단 아이콘으로 드러난다 |
| 숙소는 그날 밤 묵는 곳을 그 일차 마지막 장소로 넣는다(여러 곳 가능) | "숙소 > 장소들 > 숙소"로 하루가 보이고 숙소를 옮기는 날도 그대로 그려진다 |

### 동선 화면

| 결정 | 이유 |
|---|---|
| 일차는 선과 마커의 **색**, 이동 수단은 선 **모양**과 아이콘으로 구분한다 | 어느 날의 동선인지가 가장 중요하다. 한 채널에 두 정보를 담으면 섞인다 |
| 선 모양은 3갈래(실선: 차·버스·지하철·기차, 둥근 점선: 도보, 긴 파선: 비행기·배)이고 정확한 수단은 아이콘이 맡는다. 미정 구간은 아이콘 없는 실선이다 | 7개를 다르게 그리면 작은 화면에서 구분되지 않는다. 미정은 정상 상태라 흐리게 그리지 않는다 |
| 갈아타는 구간은 대표 수단 하나(비행기 > 배 > 기차 > 지하철 > 버스 > 차 > 도보)로 그리고, 모든 토막은 시트에서 보여 준다 | 아이콘이 여럿이면 어지럽고 갈아탄 위치를 몰라 선을 나눌 수 없다 |
| 곡률은 시트에서 고른 구간의 가운데 핸들을 지도에서 끌어 고친다 | 지도 위 모양을 보며 맞추는 쪽이 "보기 좋은 동선 이미지"라는 목적에 맞는다 |
| 일차 보기는 앞 일차의 마지막 장소(숙소가 아니어도)에서 출발한다 | 일차를 넘는 구간이 보여야 이동 수단을 적는다. 같은 장소를 또 넣게 하면 길이 0인 구간이 생긴다 |
| 같은 자리에 여러 번 넣은 장소는 마커 하나로 합친다 | 연박 숙소, 같은 공항으로 시작하고 끝나는 여행이 흔하고, 겹치면 아래 마커를 누를 수 없다 |
| 장소 필터는 숙소와 후보 둘만 두고, 칩 둘째 줄 "함께 보기"에 둔다(첫 줄은 하나만 고르는 보기) | 연박 숙소의 선이 겹쳐 어지럽고, 공유 이미지에서 머무는 곳을 감추고 싶을 수 있다. 보기와 필터가 한 줄에 있으면 헷갈렸다 |
| 숙소를 끄면 숙소에 닿는 구간은 빠지고, 낮에 들른 숙소의 앞뒤는 흐린 "숙소를 거침" 선으로 잇는다. 이 보기에서는 끌어 옮기기와 ⊕를 막고 [숙소 켜기]로 안내한다 | 끊으면 동선이 끊겨 보이고, 숙소 자리를 거치면 숨긴 위치가 드러난다. 숨긴 숙소 때문에 넣을 자리가 분명하지 않다 |
| 필터는 앱이 몰래 켜지 않는다(꺼진 필터에 저장하면 [켜기]만 알린다) | 몰래 켜면 사용자 설정이 사라진다 |
| 칩 두 줄은 첫 줄 맨 앞 ⌃로 접고, 같은 자리에 지금 보기와 켜 둔 함께 보기의 요약 알약(예: "2일차, 숙소와 후보 보기")만 남긴다. 접은 상태는 기기에 기억한다 | 지도를 넓게 본다(사용자 건의). 필터 상태가 보여야 숙소나 후보가 왜 없는지 안다. 끈 것보다 켠 것을 적는다(사용자 결정) |
| [내 위치]와 맞추기 버튼은 아래 시트 윗변을 따라 올라가고, 가운데 높이보다 더 올리면 숨는다 | 시트를 반쯤 올린 채 위치를 본다. 지도가 띠만 남으면 누를 일이 없다(사용자 결정) |
| 지도 전환은 **여행 단위**다(Stop이 모두 국내면 네이버, 하나라도 해외면 구글) | 지도를 움직일 때마다 바뀌면 깜빡이고 어색하다 |

### 일차 동선 시트와 편집

| 결정 | 이유 |
|---|---|
| 장소 상세는 따로 된 화면이 아니라 일차 동선 시트(목록)로 보여 준다 | 핵심은 "그날 어떻게 움직이나"다. 장소와 이동 방법이 함께 보이고 순서도 목록에서 끈다 |
| 시트는 깔끔하게 둔다. 연필·손잡이와 외부 지도 칸은 펼친 줄에만 있고, 장소 지우기는 입력 화면 안에 있다. 예외로 동선 사이 ⊕는 늘 보인다 | 지도에서 연 시트는 보려고 연 것이다. 버튼이 늘 보이면 어지럽고 실수하기 쉽다(실기기). 사이에 넣는 기능은 찾을 수 있어야 한다 |
| "넣을 자리" 칸은 없다. ⊕로 연 새 장소는 그 자리, 나머지는 기본 자리(맨 뒤, 마지막이 숙소면 숙소 앞, 숙소는 맨 뒤)에 들어가고 순서는 끌어 바꾼다 | 밤 숙소 뒤에 넣으면 다음 날 출발이 바뀐다. 가까운 자리에 자동으로 넣지 않는다(틀리면 이유를 모른다) |
| 입력 화면의 주소 칸이 검색 칸이다. 찾아 고르면 주소와 위치가 함께 바뀌고, 글자만 고치면 위치는 그대로다 | "장소 옮기기"도 된다. 글자마다 찾으면 호출이 많아진다 |
| 적어 둔 이동 수단이 사라지게 되면 그 구간을 먼저 보여 준다 | 모르고 넣거나 옮기면 적어 둔 정보를 잃는다 |
| 그날 밤 숙소가 없으면 시트 맨 아래에 숙소 버튼을 둔다: 그날 들른 숙소, 출발 장소가 숙소면 그 숙소(연박), 아니면 앞 일차들에서 마지막으로 들른 숙소 하나 | 찾기 없이 한 번에 넣는다. 밤샘이나 야간 이동 뒤에 원래 숙소로 돌아가는 날도 있다. 모두 내놓으면 버튼이 쌓인다(사용자 결정) |
| 가로이고 폭이 600dp 이상이면 시트 대신 오른쪽 패널이다 | 가로 화면은 세로가 짧아 시트를 올리면 둘 다 납작해진다 |
| 예정 시각과 방문 시각은 같은 휠로 1분 단위로 고른다 | 휴대폰 알람과 같아 익숙하고, 누른 순간으로 기록한 방문 시각(12:41)을 그대로 고친다(사용자 결정) |

### 후보 장소

| 결정 | 이유 |
|---|---|
| 후보는 장소(Stop)와 따로 된 모델이다. 일차·순서·사진이 없고 넣은 순서로 보여 준다 | 동선 규칙과 DB 제약이 일차·순서를 전제한다. "일차 없는 장소"로 넣으면 그 규칙을 모두 고쳐야 한다 |
| [동선에 넣기]와 [후보로 빼기]는 서버가 한 번에 바꾸고 같은 ID를 쓴다 | 나눠 보내면 중간 실패에 장소가 사라지거나 두 번 생긴다 |
| 지도: "후보" 필터(기본 켜짐)로 작은 보조 마커를 동선 마커 아래에 그리고 카메라 맞춤에 넣지 않는다 | 기본으로 보이되 동선보다 덜 띄어야 한다. 카메라가 넓어지면 동선이 작아진다 |
| 목록: 칩 줄 끝 "후보 목록" 보기. 흐린 동선 위에 후보를 진한 마커로 그리고, 시트는 넣은 순서 목록이다 | 일차 시트와 같은 자리, 같은 펼침이다. 흐린 동선 위에서 어디에 넣을지 판단한다 |
| 후보 입력은 이름·주소·종류·설명·메모뿐이다. [동선에 넣기]는 후보 값을 채운 장소 입력 화면이고, [후보로 빼기]는 장소 입력 화면에 있으며 이동 수단, 예정 시각, 사진이 사라질 때만 묻는다 | 묻는 것이 적어야 빨리 모은다. 장소와 같은 화면이라 경고를 그대로 쓴다 |
| 후보는 여행을 따라간다(휴지통, 되살리기, 영구 삭제·탈퇴). 후보 하나는 확인 창 뒤 바로 지운다 | 휴지통 대상은 여행뿐이다. 후보는 장소보다 가벼운 메모다 |
| 내보내기 이미지에는 후보를 기본으로 넣지 않고, 공유와 복사에 넣을지는 3단계에서 정한다(제안: 넣는다) | 이미지는 정해진 동선의 결과물이고, 후보는 공유받은 사람에게도 쓸모 있다 |

### 여행 중

| 결정 | 이유 |
|---|---|
| 현재 위치는 MVP에 넣고 "앱 사용 중" 권한만 쓴다. 백그라운드 위치와 GPS 기록은 없고, 화면을 나가거나 앱이 뒤로 가면 멈춘다 | 상시 기록은 배터리, 개인정보, 심사 부담이 크다 |
| 권한은 [내 위치]를 처음 누를 때 묻고 미리 설명하는 창은 없다. 여행 중이고 이미 허용했으면 열 때 묻지 않고 파란 점만 켠다. 받지 못하면(거부, 위치 꺼짐, 10초) 스낵바로 알리고 고칠 수 있으면 [설정]을 단다 | 버튼을 누른 것이 이유라 설명 창은 단계만 늘린다. 여행 중에는 열자마자 위치가 보여야 쓸모가 있다 |
| 위치는 앱이 받아 지도에 넘기고 지도 SDK의 위치 추적은 쓰지 않는다 | 권한과 안내를 앱이 정하고 구글 지도로 바꿔도 같다 |
| "근처"는 [내 위치]가 보여 주는 반경 1km다. 위치를 알면 후보 목록을 직선거리 가까운 순으로 놓고 거리를 붙인다 | 걸어서 갈 만한 거리다. 길 따라 거리는 외부 API가 필요하고 지도 앱이 맡는다 |
| 방문은 장소 줄 오른쪽 동그라미(빈 원, 방문하면 ✓)로 기록하고 지우며, 둘 다 확인 창을 거친다. 지도 마커와 번호는 방문해도 그대로다 | 글자 버튼([방문 완료])은 아직 할지 모르는 일을 크게 적고, 마커가 ✓로 바뀌면 계획한 동선을 읽기 어렵다. 확인 창은 실수를 막는다 |
| 방문은 여행 중과 후에만 있다. 기록 시각은 누른 때인데, 그 일차의 날짜가 이미 지났으면 그날의 예정 시각(없으면 낮 12시)이다. 장소 편집에서 날짜와 시각을 고친다 | 여행이 끝난 뒤 체크해도 오늘 날짜로 남지 않는다 |
| 방문 시각은 순간(UTC)으로 저장하고 장소의 시간대로 보여 준다. 서버는 PATCH의 `visitedAt` 하나로 받고(null이면 지움) 하루 넘는 미래만 막는다 | 다른 칸과 한 요청으로 저장하고 방문 여부와 시각이 어긋날 수 없다. 지난 날짜는 끝난 여행의 체크와 고치기에 필요하다 |
| 여행 기간 중에는 동선 화면을 오늘 일차로 연다 | 여행 중에 가장 먼저 보는 것이 오늘 동선이다 |

### 지출 기록과 동행 정산

| 결정 | 이유 |
|---|---|
| 2단계에서 해외(2-1)·오프라인(2-2) 뒤에 만든다. 영수증 인식은 7단계 아이디어다 | 통화·환율은 해외와 함께 설계하고, 해외에서는 인터넷 없이 적는 일이 많다 |
| 금액은 통화의 가장 작은 단위 정수다. 지출마다 기준 통화 환산 금액, 쓴 환율, 환율 출처(그날 / 직접)를 저장하고 "현재 환율로 보기"는 화면에서 계산한다 | 소수면 합계에 오차가 생긴다. 쓴 환율을 저장해야 정산이 그대로다. 카드 명세서에 맞추려면 직접 입력이 필요하다 |
| 지출은 장소에 붙이거나 장소 없이 여행에 붙인다 | 항공권, 숙소 선결제, 교통처럼 장소가 없는 지출이 많다 |
| 동행은 계정이 아니라 이름 목록이고 입력은 여행 주인만 한다 | 공동 편집을 하지 않는다는 결정을 지키며 정산한다 |
| 공유 화면에 지출·정산을 보일지는 3단계에서 정한다(제안: 주인이 켠다). 복사할 때 지출과 동행은 뺀다 | 지출은 개인 기록이다 |

### 사진, 이미지, 공유

| 결정 | 이유 |
|---|---|
| 지도 이미지는 앱에서 만들고 저장하지 않고 늘 최신 데이터로 다시 만든다. 이미지를 고치려면 여행을 고친다 | 서버 렌더링보다 간단하고 비용이 없다. 이미지 위 편집은 편집 상태를 저장해야 해서 7단계다 |
| 사진은 S3 Presigned URL로 앱이 바로 올리고, 서버는 권한 확인, URL 발급, 등록만 한다 | 서버를 거치면 대역폭과 시간이 크게 든다 |
| 앱이 원본(긴 변 1920px)과 썸네일(사용자가 고른 정사각형 400×400)을 함께 올린다. 마커, 목록, 내보내기는 썸네일, 크게 볼 때는 원본이다 | 마커마다 원본을 받으면 장소 30곳에 10MB가 넘는다. 썸네일 서버(Lambda)가 필요 없다. 보일 부분은 사진마다 달라 사용자가 고른다(실기기) |
| 1단계 개발은 S3 GET 서명 URL(1시간)로 사진을 보이고, CloudFront 서명 URL은 1-7 배포 때 바꾼다 | 사용자가 적을 때는 CDN 이득이 없다. 응답 필드는 그대로라 앱은 고치지 않는다 |
| 사진이 있는 장소의 지도 마커는 둥근 사각 사진이고 번호는 모서리 배지다 | 사진이 보이는 지도라는 목적에 맞고 자리를 덜 차지한다 |
| 사진은 앱에서 줄이고 위치 정보(EXIF)를 지운 뒤 올린다. 촬영 시각·좌표는 저장하지 않는다 | 공유되는 사진에 위치를 남기지 않는다 |
| 장소 삭제, 후보로 빼기, 영구 삭제, 탈퇴 때 S3 사진도 서버가 먼저 지운다(휴지통으로 옮길 때는 아니다). 등록하지 않은 파일은 S3 수명 주기 규칙이 하루 뒤 지운다 | 주인 없는 파일은 비용과 개인정보로 남는다 |
| 지운 여행은 30일 동안 휴지통에 둔다. 대상은 여행뿐이고 탈퇴는 바로 지운다. 휴지통의 여행은 휴지통 API 말고는 없는 여행이고(공유 링크 포함), 되살리면 원래 자리와 링크로 돌아온다 | 실수로 지운 여행을 되찾는다. 되살리면 지우기 전과 똑같아야 덜 헷갈린다 |
| 보관 기간은 서버가 정하고 한 시간마다 지운다. 앱은 서버가 준 지울 시각으로 남은 날을 보여 준다 | 기간을 바꿔도 앱 업데이트가 필요 없고, 서버가 여러 대여도 된다 |
| 제주 샘플은 휴지통에 넣지 않고 기기에서 숨긴다. 설정 화면(1-6)에 "샘플 여행 다시 보기"를 둔다 | 샘플은 앱에 담긴 안내라 서버에 없다 |
| 외부 지도 연결은 이름과 좌표로 검색 링크를 만든다(placeId가 있으면 함께). 영업시간·평점 같은 장소 정보는 앱이 받아 와 보여 주지 않는다 | MVP에는 Places가 없고 네이버 공개 API는 영업시간을 주지 않는다. 화면이 단순하다(사용자 결정) |
| 공유받은 여행은 보기만 하고, 고치려면 복사한다. 공유 화면에서 메모는 숨긴다. 공유를 끄거나 링크를 새로 발급할 수 있다 | 공동 편집은 멤버, 권한, 동시 수정이 필요해 범위가 크다. 퍼진 링크는 회수할 수 없다 |

### 지도, 외부 서비스, AI

| 결정 | 이유 |
|---|---|
| 지도와 장소 검색은 인터페이스로 나눈다(`MapProvider`, `PlaceSearchProvider`) | 구글을 붙일 때 기존 코드를 갈아엎지 않는다 |
| 국내 장소 찾기는 **주소(또는 건물명) 한 줄 + 행안부 도로명주소 검색·좌표제공 API**다. 서버가 키를 갖고 부르고, 붙여 넣은 글을 다듬어 도로명·지번까지를 검색어로, 뒤의 층·호를 상세 주소로 나눈다 | 공공데이터라 결과를 저장해도 된다. 카카오 로컬, 네이버 지역 검색, NCP 지오코딩, VWorld 지오코더는 약관이 결과 저장을 막는다 |
| 장소 찾기에서 하지 않는 것: 상호·관광지 이름 검색, 공유 링크(`naver.me` 등) 풀기, 좌표로 주소 찾기, 영어 주소 | 상호 검색 API는 위 약관 때문에 못 쓴다. 링크를 풀려면 페이지를 긁어야 한다 |
| 구글은 2단계에서 Places, AI와 함께 넣는다 | AI 좌표 검증에 Places가 필요하고, 지도만으로는 해외 검색이 안 된다 |
| **LLM이 준 좌표는 믿지 않는다** | 장소 이름만 받고 좌표는 Places로 검증한다. 검색되지 않으면 빼거나 표시한다 |
| AI 생성은 서버를 거치는 비동기 작업 + 푸시 알림이다 | 수십 초라 HTTP 타임아웃 위험이 있다. 키 보호, 횟수 제한, 캐싱, 비용 기록을 서버에서 한다 |
| 여행 중 화면은 오프라인에서도 본다(2단계) | 해외에서는 데이터가 자주 끊긴다 |

### 앱 화면과 디자인

| 결정 | 이유 |
|---|---|
| 여행 목록은 정사각형 카드 격자다 | 한 화면에 더 많이 보이고 나중에 동선 미리보기나 사진을 넣을 수 있다 |
| 화면 글자는 gen-l10n(ARB)으로 관리하고 지금은 한국어만 | 영어는 ARB만 더하면 된다 |
| 디자인 시스템은 기본 값 → 의미 토큰 → 컴포넌트 테마 3단계다. 지금은 라이트 모드만 | 화면과 내보내기 이미지가 같은 토큰을 써서 모양이 맞고, 다크 모드는 값만 더한다 |
| 글꼴은 나눔스퀘어라운드(OFL)를 앱에 넣는다 | 둥근 분위기에 맞고, 넣어야 내보낸 이미지가 기기마다 같다 |
| 주 색은 코랄(#FF6F61)이고 파랑은 현재 위치에만 쓴다 | 지도 바탕(물 파랑, 공원 초록) 위에서 잘 보인다 |
| 장소 이름은 따옴표로 감싸지 않고 여행 제목만 ‘’로 감싼다. 화면 글자에 가운뎃점(·)을 쓰지 않는다 | 장소 이름마다 따옴표가 붙으면 거슬린다(실기기). 제목은 자유 글이라 없으면 경계가 흐려진다 |
| 제주 샘플은 서버에 두지 않고 앱에 담아 보기만 되게 한다. [실제로 사용하기]는 일반 API로 내 여행에 복사한다(날짜 미정) | 완성된 동선을 먼저 보면 무엇을 하는 앱인지 바로 안다. 서버에 넣지 않아야 반쯤 들어간 샘플이 남지 않는다 |

### 로그인과 계정

| 결정 | 이유 |
|---|---|
| 앱이 SDK로 받은 토큰을 서버가 검증한다. 카카오는 **id_token**(OIDC), 네이버는 **access token**으로 프로필 API를 불러 확인한다 | 앱이 보낸 사용자 ID는 믿을 수 없다. id_token 검증은 Apple·구글에도 다시 쓴다. 네이버 Flutter SDK는 id_token을 주지 않는다 |
| 서버가 access 토큰(JWT, 15분)과 refresh 토큰(30일, DB에는 해시)을 준다. refresh는 쓸 때마다 바꾸고, 예전 토큰이 다시 오면 탈취로 보고 그 기기 로그인을 끊는다 | access는 DB를 안 봐서 서버를 늘려도 그대로고, refresh는 DB에 있어야 로그아웃·탈퇴·탈취 때 끊는다 |
| 카카오와 네이버로 따로 들어오면 계정을 잇지 않는다 | 이메일을 받지 않아 믿고 이을 값이 없고, 이메일로 합치면 남의 계정을 가로챌 수 있다 |
| 받는 정보는 닉네임(선택, 가입 때만)뿐이고 제공자 토큰은 저장하지 않는다 | 처리방침과 탈퇴가 단순하다. 탈퇴 때 연결 끊기는 앱이 SDK로 한다 |
| 제공자에 닿지 못하면 401이 아니라 503이다 | 앱이 "다시 로그인"과 "잠시 후 다시"를 나눈다 |
| 네이버 로그인 Client Secret은 APK에 들어간다(규칙의 예외). `android/local.properties`에서 매니페스트로만 넣고 Dart와 `.env`에는 두지 않는다 | SDK가 초기화에 Secret을 요구하고 PKCE는 거절됐다. 서버는 access token만 검증해서 꺼낸 Secret으로 우리 계정에 닿을 수 없다 |

### 기술과 인프라

| 결정 | 이유 |
|---|---|
| 서버는 NestJS다 | 인증, 검증, 횟수 제한, 큐, Swagger가 공식 모듈로 있고 구조가 정해져 있다 |
| 상태 관리는 Riverpod을 코드 생성 없이 쓴다 | 로딩·에러 상태를 기본으로 지원하고 저장소·지도 구현을 바꿔 끼우기 쉽다. 모델이 적어 코드 생성 부담이 더 크다 |
| 라우팅은 go_router다 | 공유 링크(딥링크)와 로그인 후 돌려보내기를 한 곳(redirect)에서 한다 |
| 테스트는 Jest와 `flutter test`이고 단계별 완료 기준에 넣는다 | 가장 널리 쓰이고 설정이 적다 |
| 처음부터 stateless다(JWT, 파일은 S3) | 서버가 여러 대가 돼도 코드를 고치지 않는다 |
| 로드밸런서는 **부하 테스트로 병목을 확인한 뒤** 넣는다 | 근거와 수치가 있는 개선 스토리가 된다 |
| iOS는 MVP 이후 맥이 있는 친구에게 부탁한다 | 빌드와 디버깅에 Xcode(macOS)가 필요하다 |

## 알아 둘 제약

- 네이버 지도는 해외 상세도가 낮고, 네이버 Directions API는 자동차 경로만 준다(그래서 직선·곡선으로 그린다).
- Firebase Dynamic Links는 2025년에 끝났다. 앱 링크는 App Links / Universal Links로 만든다.
- 스토어 출시: 개인정보처리방침(위치·사진, 수집 항목, 목적, 보관 기간, 삭제 방법), 앱 안 삭제와 웹 삭제 요청 경로(Google Play), iOS는 Apple 개발자 계정(연 $99, 본인 명의)과 Apple 로그인.
- AWS 비용: ALB는 트래픽이 없어도 기본 요금이 나오고 NAT Gateway는 비싸다. Budget 알림을 처음부터 켠다.
