# MapMarker 큰 그림

> 최종 갱신: 2026-11-03 · 단계별 계획은 [PLAN.md](PLAN.md) 참고

## 한 줄 정의

여행 동선, 구간별 이동 방법, 장소 설명과 사진을 담은 **보기 좋은 여행 동선 페이지와 이미지**를 만들고, 다시 보고, 공유하는 앱.

- 핵심 결과물은 두 가지다.
  1. **여행 동선 페이지:** 앱 안에서 보는 화면
  2. **여행 동선 이미지:** 동선이 한눈에 보이는 한 장짜리 이미지. 여행 전·중·후 모두 만들고 수정한다
- 로그인하면 **여행 목록**이 나온다. 여행마다 정사각형 카드로, 휴대폰에서는 한 줄에 2개씩(태블릿은 3~4개) 보인다. 예: "부산 2박 3일 봄 여행", "제주 3박 4일 여름 여행"
  - 하나를 고르면 동선을 따라 지도가 나온다.
  - 일차를 고르면 그날의 장소와 이동 방법이 목록으로 나오고, 장소마다 네이버 지도나 구글 맵에서 해당 장소를 여는 칸이 있다.

**해결하려는 문제:** 기존 지도 앱에서는 동선과 장소 포인트를 함께 그리기가 번거롭다.

## 프로젝트 목적

- 실제로 쓰는 서비스를 만든다.
- 포트폴리오와 이직용 경험을 쌓는다. 특히 클라이언트·서버 분리, AWS, 로드밸런싱, AI 연동 경험이 목표다.
- 원칙: **기술을 쓰려고 서비스를 만들지 않는다.** 서비스를 키우다가 필요해질 때 기술을 도입한다.
  - 도입할 때마다 `문제 → 측정 → 설계 → 적용 → 검증` 기록을 남긴다.

## 사용 시점

같은 여행(Trip)이 시점에 따라 다른 상태로 쓰인다. 기능을 따로 만들지 않고 편집 기능을 공유한다.

| 시점 | 사용자가 하는 일 |
|---|---|
| 여행 전 (계획) | 점 찍기, 구간과 이동 수단 정하기, 예정 시각과 메모 남기기, AI로 동선 초안 받기, **계획 동선 이미지 만들기** (예: 동행에게 공유) |
| 여행 중 (진행) | 현재 위치와 다음 장소 확인, 방문 체크, 사진 올리기, **진행 상황 이미지 만들기** |
| 여행 후 (회고) | 사진 붙이기, 실제로 간 대로 수정하기, **회고 이미지 만들기** |

- **여행 상태는 여행 기간으로 자동 판단한다.** 시작일 전이면 "전", 기간 중이면 "중", 종료일 후면 "후"다. 날짜를 아직 정하지 않은 여행(기간 없음)은 "전"이다. "오늘"은 사용자 기기의 날짜다.
- 사용자가 직접 바꿀 수도 있다. 예: 일정이 바뀌어 하루 일찍 출발할 때. 직접 바꾼 상태는 "자동으로 되돌리기" 전까지 유지된다.

## 핵심 기능

- **여행 목록:** 로그인 후 첫 화면이다. 여행이 정사각형 카드로 휴대폰에서는 한 줄에 2개씩(태블릿은 3~4개) 놓인다. 카드에는 상태, 제목, 기간과 일정이 보인다.
  - 제목은 기본으로 "{지역} {일정} {계절} 여행" 형태로 만들어지고(예: "부산 2박 3일 봄 여행", "경주 당일치기 가을 여행"), 사용자가 언제든지 바꿀 수 있다.
- **여행 동선 페이지:** 동선을 따라 지도가 나온다. 일차별로 보거나 여행 전체를 한 번에 볼 수 있다.
  - 일차는 선과 마커 색으로 구분한다. 일차 보기는 전날 마지막 장소(보통 전날 밤 숙소)에서 출발한다.
  - 숙소를 켜고 끌 수 있다. 장소 필터는 이것 하나다.
- **일차 동선 시트:** 일차를 고르면 그날의 장소(이름, 예정 시각, 설명, 메모, 사진)와 그 사이 구간(이동 수단)이 차례로 나온다. 세로·좁은 화면은 지도 아래 시트, 가로이고 넓은 화면은 지도 오른쪽 패널이다.
  - 지도의 포인트나 선을 누르면 그 일차로 들어가서 해당 장소·구간을 보여 준다.
  - 장소마다 **네이버 지도 / 구글 맵에서 열기** 칸이 있다. 영업시간, 리뷰 같은 정보는 외부 지도에서 본다.
  - 설명은 **사용자가 직접 쓴 내용 + Places 정보**(주소, 영업시간, 평점 등)를 나눠 보여 준다. Places 정보는 2단계에 추가한다.
  - 시트에서 장소를 끌어서 순서를 바꾸고, 장소와 구간(이동 수단)을 고치고, 장소를 지운다. 새 장소와 다른 일차로 옮기는 장소는 "넣을 자리"(그 일차의 장소 사이)를 고른다.
  - 넣거나 옮겨서 적어 둔 이동 수단이 사라지게 되면 어느 구간인지 보여 주고 먼저 묻는다.
- **동선 그리기:** 지도에 직접 점을 찍는다. GPS 기록은 나중 단계에서 추가한다.
- **구간선:** 기본은 직선이다. 구간마다 PPT 곡선처럼 둥글기를 조절할 수 있다.
- **이동 수단:** 구간마다 도보, 지하철, 버스, 기차, 차, 비행기, 배 중에서 고르고 아이콘과 선 모양으로 표시한다. 실제 도로 경로는 그리지 않는다.
  - 걸리는 시간은 모든 수단에, 정류장 수는 지하철·버스에 적을 수 있다. 갈아타면 여러 수단을 이어 적는다.
  - 예: 지하철 4정류장 / 도보 20분 / 지하철 2정류장 + 도보 / 비행기 3시간 20분 / 배 1시간 40분
- **시간:** 예정 시각과 실제 시각은 **현지 시간대와 함께** 저장한다. 해외 여행에서도 현지 시각 그대로 보인다.
- **사진:** 장소마다 사진을 1장 올린다. 사진이 없는 장소도 있다. 나중에 여러 장으로 늘어날 수 있다.
- **이미지 내보내기**
  - 동선, 이동 수단, 화살표, 장소 이름, 사진이 들어간 지도 이미지를 **앱에서** 만든다.
  - 여행 전·중·후 언제든 만들고, 다시 만들고, 수정한다. 이미지는 항상 최신 여행 데이터로 생성된다.
  - 범위(전체/일차별), 비율(1:1, 4:5, 9:16), 사진 포함 여부 같은 옵션을 고를 수 있다.
  - 앱이 없는 사람에게 공유하는 수단이기도 하다.
- **공유**
  - 앱이 있는 사람: 링크를 누르면 앱에서 해당 여행이 열린다. 공유받은 여행은 **보기만** 할 수 있다. 동선, 장소 설명, 사진은 보이고 메모(작성자의 개인 기록)는 숨긴다.
  - 앱이 없는 사람: 이미지로만 공유한다. 링크를 누르면 스토어로 이동한다.
  - **공유 끄기 / 링크 새로 발급:** 공유를 끄면 기존 링크가 더 이상 열리지 않는다. 새로 발급하면 예전 링크는 막히고 새 링크만 열린다.
- **내 여행으로 복사:** 공유받은 여행을 자기 계정에 복사해서 자유롭게 수정한다. 예: 친구가 만든 동선을 받아 내 일정에 맞게 고치기
  - 복사본은 원본과 연결되지 않고, "여행 전(계획)" 상태로 시작한다.
  - **복사하는 것:** 장소(이름, 좌표, 종류, 일차, 순서, 설명, placeId, 예정 시각), 구간(이동 수단, 곡률)
  - **복사하지 않는 것:** 사진, 메모, 방문 체크, 실제 시각
- **오프라인 보기:** 여행 중 화면은 마지막으로 불러온 여행 데이터를 기기에 저장해 두고, 인터넷이 끊겨도 보여 준다. (2단계)
- **AI 동선 생성:** 여행지, 계절, 일정(예: 3박4일)을 입력하면 AI가 동선을 만들고, 결과는 편집 가능한 일반 여행으로 생성된다.
- **로그인:** 네이버, 카카오 소셜 로그인. iOS 출시 때 Apple 로그인을 추가한다 (App Store 심사 기준)
  - 아이디·비밀번호 로그인은 없다. 받는 정보는 닉네임(선택 동의)뿐이다.
  - 같은 사람이 네이버와 카카오로 따로 들어오면 서로 다른 계정이다.
- **회원 탈퇴:** 앱 안에서 계정을 삭제할 수 있다. 여행, 사진(S3)을 포함한 사용자 데이터를 모두 지운다. 앱 밖에서 삭제를 요청할 수 있는 웹 페이지도 둔다 (Google Play 정책)
- **삭제 처리:** 여행이나 장소를 지우면 연결된 S3 사진도 함께 지운다.
- **지도**
  - 국내는 네이버 지도, 해외는 구글 지도로 **여행 단위 자동 전환**한다.
  - 사용자가 여행 설정에서 직접 바꿀 수도 있다.

## 기술 스택

| 영역 | 선택 |
|---|---|
| 앱 | Flutter. Android 먼저, iOS는 MVP 이후. 상태 관리 **Riverpod**, 라우팅 **go_router**, 다국어 **gen-l10n**(한국어 먼저, 영어는 나중에) |
| 서버 | **NestJS** (TypeScript) + **Prisma** |
| DB | PostgreSQL (AWS RDS) |
| 파일 | S3 + CloudFront |
| 인프라 | AWS. 단일 EC2로 시작해 ALB와 Auto Scaling으로 단계적으로 확장 |
| 푸시 | FCM. AI 생성 완료 알림 등 |
| 지도 / 장소 | 네이버 지도, 구글 지도 + Google Places |
| 웹 | 단순한 정적 페이지. S3 + CloudFront로 호스팅 (아래 "웹 페이지" 참고) |
| 테스트 | 서버: Jest (단위 + e2e), 앱: `flutter test` (단위 + 위젯) |
| 모바일 웹 서비스 | 지금은 고려하지 않음 |

**저장소:** GitHub 조직 [`mapmarker-dev`](https://github.com/mapmarker-dev)에서 모두 public으로 관리한다.

| [`mapmarker-app`](https://github.com/mapmarker-dev/mapmarker-app) | Flutter 앱 |

- 로컬에서는 네 저장소를 같은 부모 폴더 아래에 나란히 클론한다. 각 저장소의 `CLAUDE.md`가 `../.github/CLAUDE.md`의 공통 규칙을 불러오기 때문이다.
- 저장소를 나눈 이유: 기술 스택이 서로 다르고, 배포와 CI를 따로 돌리며, 레포별로 권한을 줄 수 있다(예: iOS를 도와줄 친구에게 앱 저장소만 공유). 조직 페이지 하나로 서비스 전체를 보여 줄 수 있어 포트폴리오에도 좋다.

### 웹 페이지

모바일 웹 서비스는 만들지 않지만, 스토어 정책과 공유 링크 때문에 **단순한 정적 웹 페이지는 꼭 필요하다.**

| 페이지 | 필요한 이유 | 단계 |
|---|---|---|
| 계정 삭제 요청 | Google Play 정책: 앱 밖에서도 계정 삭제를 요청할 수 있어야 한다. 삭제 방법 안내 + 요청 경로(문의 메일 또는 간단한 폼) | 1단계 |
| 개인정보처리방침 | 스토어 등록에 공개 URL이 필요하다 | 1단계 |
| 공유 링크 랜딩 | 앱이 없는 사람이 공유 링크를 열면 기기를 판별해 스토어로 보낸다 | 3단계 |
| `assetlinks.json` / `apple-app-site-association` | 공유 링크를 앱에서 열기 위한 App Links / Universal Links 인증 파일 | 3단계 / 6단계 |

## 데이터 구조 (뼈대)

```
User (닉네임?)
├─ SocialAccount (제공자 카카오/네이버, 제공자 사용자 ID)
├─ AuthSession (로그인한 기기 하나: refresh 토큰 해시, 만료)
└─ Trip (여행: 제목, 지역, 일정(몇 박 몇 일), 계절, 기간?(시작일·종료일, 없으면 날짜 미정),
   │      직접 바꾼 상태?(없으면 기간으로 자동), 지도 provider 자동/수동,
   │      생성 출처 직접/AI/복사, 복사 원본 Trip?, 공유 ID?(공유를 끄면 비움))
   ├─ Stop (장소: 좌표, 이름, 종류(숙소/음식/관광/기타), 일차, 순서, 설명, 메모, 방문 여부,
   │        예정 시각(일차 + 현지 시:분), 실제 시각(순간), 시간대(예: Europe/Paris),
   │        placeProvider?, placeId?)
   │    └─ Photo (S3 키. 지금은 장소당 1장)
   └─ Segment (Stop A → Stop B: 이동 수단 목록(수단 + 정류장 수? + 걸리는 시간?),
               곡률 k, 타입 일반 / GPS 트랙)
```

ID는 앱이 UUID v7로 만든다. 구간 ID와 공유 ID만 서버가 만든다.

## 주요 결정과 이유

화면 동작의 세부(크기, 거리, 어느 탭에서 무엇이 뜨는지)와 그 이유는 앱 코드 주석과 테스트에 있다. 여기에는 다시 바꾸려면 기획부터 봐야 하는 결정만 둔다.

### 데이터와 시간

| 결정 | 이유 |
|---|---|
| ID는 앱이 UUID v7로 만든다. 구간 ID는 서버가 UUID v7로, 공유 ID는 서버가 무작위로 만든다 | 앱이 만든 ID는 서버 ID로 바꿔 끼울 필요가 없고, 같은 요청을 다시 보내도 중복되지 않는다. v7은 만든 시각 순서라 DB 인덱스에 유리하다. 구간은 사용자가 만드는 것이 아니라 장소 순서에서 따라 나와서, 서버가 장소를 넣고 옮기고 지울 때 앱과 같은 규칙으로 만들고 지운다. 응답에 그 여행의 장소와 구간 전체를 담아서 앱은 받은 값으로 바꾸면 된다. 공유 ID는 추측할 수 없어야 한다 |
| 여행 상태(전/중/후)는 앱이 기기의 오늘 날짜와 기간으로 계산하고, 서버에는 사용자가 직접 바꾼 상태만 저장한다 | 저장한 자동 상태는 날이 지나면 낡는다. 서버는 사용자 기기의 시간대를 몰라 날짜가 하루 어긋날 수 있다(서버가 UTC면 한국 오전 9시 전에는 전날) |
| 기간은 시간대 없는 날짜, 예정 시각은 일차 + 현지 시:분, 실제 시각은 순간(UTC)과 현지 시간대로 둔다 | 시간대 없이 저장하면 해외 여행의 시각이 틀어진다. 예정 시각에 날짜를 넣지 않으면 기간이 없는 여행에도 넣을 수 있고, 날짜를 옮기거나 복사해도 그대로 맞는다(날짜는 시작일 + (일차 − 1)) |
| 장소는 (일차, 순서)로 늘어선 한 줄이고, 구간은 이웃한 두 장소 사이에 자동으로 만들고 지운다. 일차를 넘어서도 잇는다. 이웃이 바뀐 구간의 이동 수단은 사라진다 | 사용자가 선을 따로 잇지 않아도 되고 "구간 = 선"으로 단순해진다. 전날 숙소에서 다음 날 첫 장소로 가는 길, 야간 비행기·배도 구간이 된다. 이웃이 바뀌면 경로가 바뀐 것이다 |
| 이동 수단은 구간마다 여러 토막(수단 + 정류장 수 + 걸리는 시간)으로 담는다. 서버는 이 목록을 JSON 칼럼(jsonb) 하나에 담고, 안의 모양은 API가 검사한다 | 실제 이동은 "지하철 2정류장 + 도보"처럼 갈아타는 경우가 많다. 목록은 늘 통째로 읽고 바꿔서 별도 테이블로 나눌 이유가 없다. 목록 안을 질의할 일이 생기면 그때 테이블로 옮긴다 |
| 곡선은 구간마다 곡률 `k` 하나만 저장한다(0이면 직선, 부호가 휘는 방향, −1~1). 앱이 메르카토르 좌표에서 2차 베지어로 그린다 | 저장은 단순하고, 지도 종류와 관계없이 똑같이 그려진다. 위도·경도로 계산하면 모양이 찌그러진다. 날짜변경선을 넘는 구간은 따로 처리한다 |
| Segment 타입은 "일반 / GPS 트랙"으로 나눈다 | 직선과 곡선은 `k`로 구분된다. 타입은 그리는 방식이 다른 GPS 트랙을 구분하는 데만 쓴다 |
| 장소 종류는 숙소·음식·관광·기타 4개다. 숙소만 동선 규칙이 있다 | 고를 때 헷갈리지 않게 적게 둔다. 종류는 늘리기는 쉽고 나누기는 어렵다. 교통(공항·역)은 이동 수단 아이콘으로 드러난다 |
| 숙소는 그날 밤 묵는 곳을 그 일차 마지막 장소로 넣는다. 한 여행에 숙소가 여러 곳일 수 있다 | 밤마다 한 번만 넣어도 "숙소 > 장소들 > 숙소"로 하루가 보이고, 숙소를 옮기는 날도 그대로 그려진다 |

### 동선 화면

| 결정 | 이유 |
|---|---|
| 일차는 선과 마커의 **색**으로, 이동 수단은 선 **모양**과 아이콘으로 구분한다 | 여행 전체 보기에서 어느 날의 동선인지 한눈에 보이는 것이 가장 중요하다. 한 채널(색)에 두 정보를 담으면 섞인다 |
| 선 모양은 3갈래(실선: 차·버스·지하철·기차, 둥근 점선: 도보, 긴 파선: 비행기·배)만 두고 정확한 수단은 아이콘이 맡는다. 미정 구간은 실선에 아이콘이 없다 | 7개를 모두 다르게 그리면 작은 화면에서 구분되지 않는다. 미정은 고르지 않아도 되는 정상 상태라 흐리게 그리지 않는다 |
| 갈아타는 구간은 대표 수단 하나(비행기 > 배 > 기차 > 지하철 > 버스 > 차 > 도보)로 선 모양과 아이콘을 정한다. 모든 토막은 시트에서 보여 준다 | 한 구간에 아이콘을 여럿 그리면 어지럽고, 갈아탄 위치를 몰라 선을 나눠 그릴 수 없다. 걸리는 시간은 비울 수 있어서 수단 순서로 고른다 |
| 진행 방향 화살표는 저장하지 않고 구간 가운데에, 수단 아이콘은 1/4 지점(출발 쪽)에 그린다. 선이 화면에서 짧아지면 숨긴다 | 방향은 이미 구간에 있다. 끝점에 두면 도착 마커에 가린다. 1/4 지점이면 마커·아이콘·화살표가 고르게 떨어지고 "지하철을 타고 떠난다"로 읽힌다 |
| 곡률은 지도에서 구간 가운데의 핸들(화살표가 든 원)을 끌어 고친다. 핸들은 시트에서 그 구간 줄을 직접 고른 때만 뜨고, 직선 가까이 끌면 직선에 붙는다 | PPT 곡선처럼 지도 위 모양을 보며 손으로 맞추는 쪽이 "보기 좋은 동선 이미지"라는 목적에 맞는다 |
| 일차 보기는 앞 일차의 마지막 장소에서 출발한다. 숙소가 아니어도 된다(공항, 야간 이동) | 일차를 넘는 구간이 다음 날 보기에 보여야 이동 수단을 적고 고칠 수 있다. 같은 장소를 다음 날 또 넣게 하면 길이 0인 구간이 생기고 야간 이동을 담지 못한다 |
| 같은 자리에 여러 번 넣은 장소는 지도에서 마커 하나로 합친다 | 연박한 숙소, 같은 공항으로 시작하고 끝나는 여행이 흔하다. 마커가 겹치면 아래 마커를 누를 수 없다 |
| 장소 필터는 숙소 켜기/끄기 하나만 둔다 | 같은 숙소에 여러 날 묵으면 드나드는 선이 겹쳐 어지럽고, 이미지로 공유할 때 머무는 곳을 감추고 싶을 수 있다(개인정보) |
| 숙소를 끄면 숙소에 닿는 구간은 빠지고, 낮에 들른 숙소의 앞뒤는 흐린 "숙소를 거침" 선(가는 파선, 누를 수 없음)으로 바로 잇는다. 하루가 끝나는 밤 숙소는 잇지 않는다 | 끊어 두면 하루 동선이 끊겨 보인다. 숙소 자리를 거쳐 이으면 숨긴 위치가 드러나고, 보통 선으로 이으면 가지 않은 길이 공유 이미지에 남는다 |
| 숙소를 끈 보기에서는 끌어 옮기기를 막고 [숙소 켜기]로 안내한다. 필터는 앱이 몰래 켜지 않는다 | 숨긴 숙소가 사이에 섞여 있어 끌어 놓은 자리가 화면에서 분명하지 않고, 보이지 않던 구간의 이동 수단이 지워진다 |
| 지도 전환은 화면이 아니라 **여행 단위**로 한다. Stop이 모두 국내면 네이버, 하나라도 해외면 구글 | 지도를 움직일 때마다 바뀌면 화면이 깜빡이고 어색하다 |

### 일차 동선 시트와 편집

| 결정 | 이유 |
|---|---|
| 장소 상세는 장소 하나의 화면이 아니라 일차 동선 시트(목록)로 보여 준다 | 이 앱의 핵심은 장소 하나보다 "그날 어떻게 움직이나"다. 장소와 이동 방법이 함께 보이고, 순서 바꾸기도 목록에서 끈다 |
| 시트는 깔끔하게 둔다. 고치기(연필)·순서 바꾸기(손잡이)는 시트에서 직접 누른 줄에만 뜨고, 장소 지우기는 장소 입력 화면 안에 둔다 | 지도에서 눌러 연 시트는 보려고 연 것이다. 버튼이 늘 보이면 어지럽고 실수로 지우거나 옮기기 쉽다 |
| 가로이고 폭이 600dp 이상이면 시트 대신 지도 오른쪽 패널로 보여 준다 | 가로 화면은 세로가 짧아서 아래 시트를 올리면 지도와 목록이 모두 납작해진다. 오른쪽에 두면 왼쪽 아래 지도 로고도 가리지 않는다 |
| 새 장소와 다른 일차로 옮기는 장소는 "넣을 자리" 칸에서 그 일차의 장소 사이를 고른다. 기본은 맨 뒤이고, 마지막이 숙소면 숙소 앞이다. 그날 밤 숙소 뒤에는 숙소만 넣을 수 있다 | 기본 자리에 들어가 엉뚱한 구간의 이동 수단이 지워지는 일을 막는다. 밤 숙소 뒤에 장소를 넣으면 그 숙소가 낮에 들른 숙소가 되어 다음 날 출발이 바뀐다(실기기에서 헷갈림 확인). 가까운 자리에 자동으로 넣지 않는다(틀렸을 때 이유를 알 수 없다) |
| 넣거나 옮겨서 적어 둔 이동 수단이 사라지게 되면, 그 구간을 일차와 함께("2일차 용두암 → 동문시장") 먼저 보여 준다. 장소 입력 화면은 "넣을 자리" 칸 아래에 미리 보여 주고, 끌기와 연박은 대화상자로 묻는다 | 모르고 넣거나 옮기면 적어 둔 정보를 잃는다. 끼어드는 자리의 구간도 사라져서 어느 구간인지 보여 줘야 판단할 수 있다. 입력 화면은 자리를 고르면서 바로 보니 저장할 때 다시 묻지 않는다 |

### 사진, 이미지, 공유

| 결정 | 이유 |
|---|---|
| 핵심 결과물은 여행 동선 페이지와 여행 동선 이미지, 두 가지다 | 페이지는 앱 안에서 다시 보고 장소 정보를 확인하는 용도다. 이미지는 여행 전·중·후 모두 만들어 공유하는 핵심 기능이다 |
| 지도 이미지는 앱에서 만들고, 저장하지 않고 항상 최신 여행 데이터로 다시 만든다. 이미지를 고치려면 여행 데이터를 고친다 | 서버 렌더링보다 훨씬 간단하고 서버 비용이 없다. 이미지 위에서 따로 편집하는 기능은 편집 상태를 저장해야 해서 7단계 아이디어로 미룬다 |
| 이미지 내보내기 기술 검증을 0단계에서 먼저 한다 | Top 2 기능인데 네이티브 지도 스냅샷이라는 기술 위험이 있다. 위험한 것부터 확인한다 |
| 사진은 S3 Presigned URL로 앱에서 S3에 바로 올린다. 서버는 권한 확인, URL 발급, 업로드 후 등록만 한다 | 사진이 서버를 거치면 대역폭·메모리·시간을 크게 쓰고 전송량도 두 배가 된다. 보안은 URL 유효 시간, 경로, 파일 형식·크기 제한으로 지킨다 |
| 사진은 앱에서 크기를 줄이고 위치 정보(EXIF)를 지운 뒤 올린다. 촬영 시각·좌표는 저장하지 않는다 | 공유되는 사진에 위치를 남기지 않는다(개인정보). 쓰는 기능이 없으니 저장하지 않는다. 업로드 시간과 S3 비용도 준다 |
| 여행·장소를 지우거나 회원 탈퇴하면 S3 사진도 지운다. DB에서 사진은 장소 삭제를 막고(Restrict), 서버가 사진과 S3 파일부터 지운다. S3 키는 `users/{userId}/trips/{tripId}/photos/{photoId}.jpg`다 | DB만 지우면 주인 없는 파일이 남아 비용이 들고 개인정보도 남는다. 막아 두면 S3를 빠뜨린 삭제가 바로 실패해 드러난다. 사용자·여행 접두어로 묶으면 남은 파일까지 한 번에 치울 수 있다 |
| 외부 지도 연결은 장소 이름과 좌표로 검색 링크를 만든다(네이버: `https://map.naver.com/p/search/{이름}?c={경도},{위도},15,0,0,0,dh`). placeId가 있으면 함께 쓴다 | MVP에는 Places 연동이 없어 이름과 좌표만 있다. 네이버 공개 API는 영업시간을 주지 않아서 이런 정보는 외부 지도에서 보게 한다 |
| 장소 설명은 사용자 작성 내용과 Places 정보를 나눠 표시한다 | 개인 기록과 객관적인 정보를 구분한다. Places 정보는 placeId로 조회해서 2단계부터 가능하다 |
| 공유받은 여행은 보기만 하고, 수정하려면 내 여행으로 복사한다 | 공동 편집은 멤버, 권한, 동시 수정 충돌 처리가 필요해 범위가 크다. 복사로 같은 목적(친구 동선을 받아 쓰기)을 훨씬 단순하게 해결한다 |
| 공유 화면에서 메모는 숨기고, 복사할 때 사진과 메모는 뺀다. 예정 시각은 복사한다 | 사진과 메모는 원본 작성자의 개인 기록이다. 사진 파일을 같이 쓰면 원본에서 지울 때 복사본이 깨지고, 복제하면 S3 비용이 든다. 시간 순서는 그 자체가 동선 정보다 |
| 공유를 끄거나 링크를 새로 발급할 수 있다 | 링크는 한 번 퍼지면 회수할 수 없다. 잘못 보냈거나 더 공개하고 싶지 않을 때 막을 수단이 필요하다 |

### 지도, 외부 서비스, AI

| 결정 | 이유 |
|---|---|
| 지도와 장소 검색은 인터페이스로 분리한다 (`MapProvider`, `PlaceSearchProvider`) | 구글을 붙일 때 기존 코드를 갈아엎지 않기 위해서 |

| AI 생성은 비동기 작업 + 푸시 알림으로 처리하고, 서버를 거쳐서만 호출한다 | 생성이 수십 초 걸려 HTTP 타임아웃 위험이 있다. API 키 보호, 사용자별 횟수 제한, 캐싱, 비용 기록, 프롬프트 버전 관리를 서버에서 한다 |
| 여행 중 화면은 오프라인에서도 볼 수 있게 한다 (2단계) | 해외에서는 데이터가 끊기는 일이 흔하다. 해외 지원과 함께 넣는다 |
| 여행 중 현재 위치 표시는 MVP에 넣고, GPS 기록은 "기록 시작 → 종료" 세션 방식으로 MVP에서 뺀다 | 현재 위치는 "앱 사용 중" 권한만으로 충분하고 간단하다. 상시 기록은 배터리, 개인정보, 스토어 심사 부담이 크고, 세션 방식도 백그라운드 위치 처리가 필요하다 |

### 앱 화면과 디자인

| 결정 | 이유 |
|---|---|
| 여행 목록은 정사각형 카드 격자다. 휴대폰은 한 줄에 2개, 태블릿은 폭에 따라 3~4개다 | 한 화면에 여행이 더 많이 보이고, 나중에 카드에 동선 미리보기나 사진을 넣을 수 있다 |
| 화면 글자는 Flutter gen-l10n(ARB)으로 관리하고 모델에는 글자를 두지 않는다. 지금은 한국어만 넣는다 | 영어를 넣을 때 ARB 파일만 더하면 된다. Flutter 공식 도구라 build_runner가 필요 없다 |
| 디자인 시스템은 기본 값 → 의미 토큰 → 컴포넌트 테마 3단계로 만든다. 지금은 라이트 모드만 만든다 | 화면과 내보내기 이미지가 같은 토큰을 써서 모양이 맞고, 색을 바꿀 때 한 곳만 고친다. 다크 모드는 나중에 값만 더한다 |
| 글꼴은 나눔스퀘어라운드(네이버, OFL)를 앱에 넣는다 | 둥근 글꼴이 서비스의 귀여운 분위기에 맞고 한글 11,172자를 모두 담는다. 앱에 넣어야 내보낸 이미지가 기기마다 같은 글꼴로 나온다 |
| 주 색은 코랄(#FF6F61)이다 | 지도 바탕(물은 파랑, 공원은 초록) 위에서 동선이 잘 보인다. 파랑은 지도 앱에서 현재 위치를 뜻해서 그 용도로 남겨 둔다 |

### 로그인과 계정

| 결정 | 이유 |
|---|---|
| 앱이 카카오·네이버 SDK로 받은 토큰을 서버가 검증한다. 카카오는 **id_token**(OpenID Connect)을 카카오 공개키로 서명·발급자·대상 앱(`aud`)·만료까지 확인하고, 네이버는 **access token**으로 네이버 프로필 API를 불러 확인한다 | 앱이 보낸 사용자 ID는 믿을 수 없다. id_token은 로그인마다 카카오를 부르지 않아도 되고, Apple·구글도 같은 방식이라 검증 코드를 다시 쓴다. 네이버 Flutter SDK는 id_token을 주지 않는다. 네이버 사용자 ID는 앱마다 달라서 다른 앱의 토큰으로 우리 계정에 닿지 못한다 |
| 검증 뒤에는 서버가 직접 access 토큰(JWT, 15분)과 refresh 토큰(30일)을 준다. refresh 토큰은 JWT가 아닌 무작위 문자열이고 DB에는 해시만 둔다. 쓸 때마다 바꾸고, 이미 바뀐 예전 토큰이 다시 오면 탈취로 보고 그 기기의 로그인을 끊는다 | 제공자 토큰에 매번 기대지 않고 서버 API를 같은 방식으로 지킨다. access 토큰은 DB를 안 봐서 서버를 늘려도 그대로고, refresh 토큰은 DB에 있어야 로그아웃·탈퇴·탈취 때 강제로 끊을 수 있다 |
| 같은 사람이 카카오와 네이버로 따로 들어와도 계정을 잇지 않는다 | 둘을 믿고 이을 공통 값이 없다(이메일을 받지 않는다). 이메일로 합치면 한쪽의 확인되지 않은 이메일로 남의 계정을 가로챌 수 있다. 사용자 하나에 소셜 계정 여러 개를 둘 수 있게 만들어서 나중에 직접 잇는 기능은 더할 수 있다 |
| 받는 정보는 닉네임(선택 동의, 가입 때만)뿐이다. 이메일·이름·사진·전화번호와 제공자 토큰은 저장하지 않는다 | 개인정보를 최소로 두면 처리방침과 탈퇴가 단순하다. 서버는 제공자 API를 부를 일이 없어서 제공자 토큰이 필요 없다. 탈퇴 때 제공자 연결 끊기는 앱이 SDK로 한다 |
| 제공자에 닿지 못하면 401이 아니라 503으로 답한다 | 앱이 "다시 로그인"과 "잠시 후 다시"를 구분해서 보여 준다 |

### 기술과 인프라

| 결정 | 이유 |
|---|---|
| 서버는 NestJS를 쓴다 | 인증, 검증, 횟수 제한, 큐, Swagger가 공식 모듈로 있다. 구조가 정해져 있어 유지보수하기 쉽다 |
| Flutter 상태 관리는 Riverpod을 코드 생성 없이 쓴다 | 서버 데이터의 로딩·에러 상태를 기본으로 지원하고, 저장소·지도 구현을 바꿔 끼우기 쉽다(서버 전에는 메모리 저장소, 테스트에서는 가짜 지도). 코드 생성은 모델이 적은 지금은 부담이 더 크다 |
| Flutter 라우팅은 go_router를 쓴다 | 3단계 공유 링크(딥링크)를 경로 표로 화면에 연결하고, 로그인 후 원래 화면으로 돌려보내는 처리를 한 곳(redirect)에서 한다 |
| 테스트는 각 진영의 기본 도구(Jest, `flutter test`)를 쓰고, 단계별 완료 기준에 포함한다 | 가장 널리 쓰여 자료가 많고 설정이 적다 |
| 처음부터 stateless로 만든다 (JWT 인증, 파일은 S3) | 서버가 여러 대가 돼도 코드를 고치지 않게 하기 위해서 |
| 로드밸런서는 **부하 테스트로 병목을 확인한 뒤** 도입한다 | 처음부터 붙이는 것보다 근거와 수치가 있는 개선 스토리가 된다 |
| iOS는 MVP 이후, 맥이 있는 친구에게 부탁한다 | iOS 빌드와 디버깅에는 Xcode(macOS)가 필요하다 |

## 알아 둘 제약

- 네이버 지도는 해외 상세도가 낮고, 네이버 장소 검색은 사실상 국내 전용이다.
- 네이버 Directions API는 자동차 경로만 제공한다. 그래서 실제 경로 대신 직선·곡선으로 그린다.
- Firebase Dynamic Links는 2025년에 종료됐다. 앱 링크는 App Links / Universal Links로 직접 구현한다.
- 스토어 출시에 필요한 것
  - **개인정보처리방침:** 위치와 사진을 다루기 때문에 필수다. 실제로 쓸 때 수집 항목, 이용 목적, 보관 기간, 삭제 방법을 자세히 조사해서 작성한다.
  - **계정 삭제:** Google Play는 계정을 만드는 앱에 앱 안 삭제 기능과 웹 삭제 요청 경로를 요구한다.
  - **iOS:** Apple 개발자 계정(연 $99)이 필요하고 본인 명의로 만든다. 소셜 로그인이 있으면 Apple 로그인도 필요하다.
- AWS 비용에 주의한다.
  - ALB는 트래픽이 없어도 기본 요금이 나온다.
  - NAT Gateway는 비싸다.
  - Budget 알림을 처음부터 켜 둔다.
