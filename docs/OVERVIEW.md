# MapMarker 큰 그림

> 최종 갱신: 2026-10-15 · 단계별 계획은 [PLAN.md](PLAN.md) 참고

## 한 줄 정의

여행 동선, 구간별 이동 방법, 장소 설명과 사진을 담은 **보기 좋은 여행 동선 페이지와 이미지**를 만들고, 다시 보고, 공유하는 앱.

- 핵심 결과물은 두 가지다.
  1. **여행 동선 페이지:** 앱 안에서 보는 화면
  2. **여행 동선 이미지:** 동선이 한눈에 보이는 한 장짜리 이미지. 여행 전·중·후 모두 만들고 수정한다
- 로그인하면 **여행 목록**이 나온다. 여행마다 정사각형 카드로, 휴대폰에서는 한 줄에 2개씩(태블릿은 3~4개) 보인다. 예: "부산 2박 3일 봄 여행", "제주 3박 4일 여름 여행"
  - 하나를 고르면 동선을 따라 지도가 나온다.
  - 포인트를 누르면 장소 설명이 나오고, 네이버 지도나 구글 맵에서 해당 장소를 여는 버튼이 있다.

**해결하려는 문제:** 기존 지도 앱에서는 동선과 장소 포인트를 함께 그리기가 번거롭다.

## 프로젝트 목적

- 실제로 쓰는 서비스를 만든다.
- 포트폴리오와 이직용 경험을 쌓는다. 특히 클라이언트·서버 분리, AWS, 로드밸런싱, AI 연동 경험이 목표다.
- 원칙: **기술을 쓰려고 서비스를 만들지 않는다.** 서비스를 키우다가 필요해질 때 기술을 도입한다.
  - 도입할 때마다 `문제 → 측정 → 설계 → 적용 → 검증` 기록을 남긴다.

## 사용 시점

같은 여행(Trip)이 시점에 따라 다른 상태로 쓰인다. 기능을 따로 만들지 않고 편집 기능을 공유한다.

| 시점 | 사용자가 하는 일 |
|---|---|
| 여행 전 (계획) | 점 찍기, 구간과 이동 수단 정하기, 예정 시각과 메모 남기기, AI로 동선 초안 받기, **계획 동선 이미지 만들기** (예: 동행에게 공유) |
| 여행 중 (진행) | 현재 위치와 다음 장소 확인, 방문 체크, 사진 올리기, **진행 상황 이미지 만들기** |
| 여행 후 (회고) | 사진 붙이기, 실제로 간 대로 수정하기, **회고 이미지 만들기** |

- **여행 상태는 여행 기간으로 자동 판단한다.** 시작일 전이면 "전", 기간 중이면 "중", 종료일 후면 "후"다. 날짜를 아직 정하지 않은 여행(기간 없음)은 "전"이다. "오늘"은 사용자 기기의 날짜다.
- 사용자가 직접 바꿀 수도 있다. 예: 일정이 바뀌어 하루 일찍 출발할 때. 직접 바꾼 상태는 "자동으로 되돌리기" 전까지 유지된다.

## 핵심 기능

- **여행 목록:** 로그인 후 첫 화면이다. 여행이 정사각형 카드로 휴대폰에서는 한 줄에 2개씩(태블릿은 3~4개) 놓인다. 카드에는 상태, 제목, 기간과 일정이 보인다.
  - 제목은 기본으로 "{지역} {일정} {계절} 여행" 형태로 만들어지고(예: "부산 2박 3일 봄 여행", "경주 당일치기 가을 여행"), 사용자가 언제든지 바꿀 수 있다.
- **여행 동선 페이지:** 동선을 따라 지도가 나온다. 일차별로 보거나 여행 전체를 한 번에 볼 수 있다.
- **장소 상세:** 포인트를 누르면 이름, 설명, 메모, 사진이 나온다.
  - 설명은 **사용자가 직접 쓴 내용 + Places 정보**(주소, 영업시간, 평점 등)를 섞어서 보여 준다. Places 정보는 2단계에 추가한다.
  - **네이버 지도 / 구글 맵에서 열기** 버튼으로 외부 지도에 연결한다.
- **동선 그리기:** 지도에 직접 점을 찍는다. GPS 기록은 나중 단계에서 추가한다.
- **구간선:** 기본은 직선이다. 구간마다 PPT 곡선처럼 둥글기를 조절할 수 있다.
- **이동 수단:** 구간마다 도보, 지하철, 버스, 기차, 차, 비행기, 배 중에서 고르고 아이콘과 선 스타일로 표시한다. 실제 도로 경로는 그리지 않는다.
  - 수단마다 정류장 수나 걸리는 시간을 적을 수 있고, 갈아타면 여러 수단을 이어 적는다.
  - 예: 지하철 4정류장 / 버스 3정류장 / 도보 20분 / 지하철 2정류장 + 도보 / 버스 1정류장 + 도보 / 비행기 3시간 20분 / 배 1시간 40분
- **시간:** 예정 시각과 실제 시각은 **현지 시간대와 함께** 저장한다. 해외 여행에서도 현지 시각 그대로 보인다.
- **사진:** 장소마다 사진을 1장 올린다. 사진이 없는 장소도 있다. 나중에 여러 장으로 늘어날 수 있다.
- **이미지 내보내기**
  - 동선, 이동 수단, 화살표, 장소 이름, 사진이 들어간 지도 이미지를 **앱에서** 만든다.
  - 여행 전·중·후 언제든 만들고, 다시 만들고, 수정한다. 이미지는 항상 최신 여행 데이터로 생성된다.
  - 범위(전체/일차별), 비율(1:1, 4:5, 9:16), 사진 포함 여부 같은 옵션을 고를 수 있다.
  - 앱이 없는 사람에게 공유하는 수단이기도 하다.
- **공유**
  - 앱이 있는 사람: 링크를 누르면 앱에서 해당 여행이 열린다. 공유받은 여행은 **보기만** 할 수 있다.
    - 보이는 것: 동선, 장소 설명, 사진
    - 숨기는 것: 메모 (작성자의 개인 기록)
  - 앱이 없는 사람: 이미지로만 공유한다. 링크를 누르면 스토어로 이동한다.
  - **공유 끄기 / 링크 새로 발급:** 공유를 끄면 기존 링크가 더 이상 열리지 않는다. 새로 발급하면 예전 링크는 막히고 새 링크만 열린다.
- **내 여행으로 복사:** 공유받은 여행을 자기 계정에 복사해서 자유롭게 수정한다. 예: 친구가 만든 동선을 받아 내 일정에 맞게 고치기
  - 복사본은 원본과 연결되지 않는다. 원본이 바뀌어도 복사본은 바뀌지 않는다.
  - 복사본은 "여행 전(계획)" 상태로 시작한다.
  - **복사하는 것:** 장소(이름, 좌표, 일차, 순서, 설명, placeId, 예정 시각), 구간(이동 수단, 곡률)
  - **복사하지 않는 것:** 사진, 메모, 방문 체크, 실제 시각
- **오프라인 보기:** 여행 중 화면은 마지막으로 불러온 여행 데이터를 기기에 저장해 두고, 인터넷이 끊겨도 보여 준다. (2단계)
- **AI 동선 생성:** 여행지, 계절, 일정(예: 3박4일)을 입력하면 AI가 동선을 만들고, 결과는 편집 가능한 일반 여행으로 생성된다.
- **로그인:** 네이버, 카카오 소셜 로그인. iOS 출시 때 Apple 로그인을 추가한다 (App Store 심사 기준)
- **회원 탈퇴:** 앱 안에서 계정을 삭제할 수 있다. 여행, 사진(S3)을 포함한 사용자 데이터를 모두 지운다. 앱 밖에서 삭제를 요청할 수 있는 웹 페이지도 둔다 (Google Play 정책)
- **삭제 처리:** 여행이나 장소를 지우면 연결된 S3 사진도 함께 지운다.
- **지도**
  - 국내는 네이버 지도, 해외는 구글 지도로 **여행 단위 자동 전환**한다.
  - 사용자가 여행 설정에서 직접 바꿀 수도 있다.

## 기술 스택

| 영역 | 선택 |
|---|---|
| 앱 | Flutter. Android 먼저, iOS는 MVP 이후. 상태 관리 **Riverpod**, 라우팅 **go_router**, 다국어 **gen-l10n**(한국어 먼저, 영어는 나중에) |
| 서버 | **NestJS** (TypeScript) + **Prisma** |
| DB | PostgreSQL (AWS RDS) |
| 파일 | S3 + CloudFront |
| 인프라 | AWS. 단일 EC2로 시작해 ALB와 Auto Scaling으로 단계적으로 확장 |
| 푸시 | FCM. AI 생성 완료 알림 등 |
| 지도 / 장소 | 네이버 지도, 구글 지도 + Google Places |
| 웹 | 단순한 정적 페이지. S3 + CloudFront로 호스팅 (아래 "웹 페이지" 참고) |
| 테스트 | 서버: Jest (단위 + e2e), 앱: `flutter test` (단위 + 위젯) |
| 모바일 웹 서비스 | 지금은 고려하지 않음 |

### 웹 페이지

모바일 웹 서비스는 만들지 않지만, 스토어 정책과 공유 링크 때문에 **단순한 정적 웹 페이지는 꼭 필요하다.**

| 페이지 | 필요한 이유 | 단계 |
|---|---|---|
| 계정 삭제 요청 | Google Play 정책: 앱 밖에서도 계정 삭제를 요청할 수 있어야 한다. 삭제 방법 안내 + 요청 경로(문의 메일 또는 간단한 폼) | 1단계 |
| 개인정보처리방침 | 스토어 등록에 공개 URL이 필요하다 | 1단계 |
| 공유 링크 랜딩 | 앱이 없는 사람이 공유 링크를 열면 기기를 판별해 스토어로 보낸다 | 3단계 |
| `assetlinks.json` / `apple-app-site-association` | 공유 링크를 앱에서 열기 위한 App Links / Universal Links 인증 파일 | 3단계 / 6단계 |

## 데이터 구조 (뼈대)

```
User
└─ Trip (여행: 제목, 지역, 일정(몇 박 몇 일), 계절, 기간?(시작일·종료일, 없으면 날짜 미정),
   │      직접 바꾼 상태?(없으면 기간으로 자동), 지도 provider 자동/수동,
   │      생성 출처 직접/AI/복사, 복사 원본 Trip?, 공유 ID?(공유를 끄면 비움))
   ├─ Stop (장소: 좌표, 이름, 일차, 순서, 설명, 메모, 방문 여부,
   │        예정 시각(일차 + 현지 시:분), 실제 시각(순간), 시간대(예: Europe/Paris),
   │        placeProvider?, placeId?)
   │    └─ Photo (S3 키. 지금은 장소당 1장)
   └─ Segment (Stop A → Stop B: 이동 수단 목록(수단 + 정류장 수? + 걸리는 시간?),
               곡률 k, 타입 일반 / GPS 트랙)
```

ID는 앱이 UUID v7로 만든다. 공유 ID만 서버가 만든다.

## 주요 결정과 이유

| 결정 | 이유 |
|---|---|
| 곡선은 구간마다 **곡률 `k` 하나만 저장**한다 (0이면 직선, 부호가 휘는 방향) | 저장은 단순하게, 렌더링은 앱에서 2차 베지어 곡선을 계산한다. 지도 종류와 관계없이 똑같이 그려진다 |
| Segment 타입은 "일반 / GPS 트랙"으로 나눈다 | 직선과 곡선은 `k` 값으로 구분되니 타입이 따로 필요 없다. 타입은 그리는 방식이 다른 GPS 트랙을 구분하는 데만 쓴다 |
| 곡선 계산은 메르카토르 투영 좌표 기준으로 한다 | 위도·경도로 계산하면 모양이 찌그러진다. 날짜변경선을 넘는 구간은 별도로 처리한다 |
| 여행 상태(전/중/후)는 기간으로 자동 판단하고, 사용자가 바꿀 수 있다 | 대부분은 자동으로 맞고, 일정이 바뀐 경우만 직접 고치면 된다. 이미지와 화면을 시점에 맞게 보여 주는 데 쓴다 |
| 자동 상태는 저장하지 않고 앱이 기기의 오늘 날짜로 계산한다. 서버에는 직접 바꾼 상태만 저장한다 | 저장한 자동 상태는 날이 지나면 낡는다. 서버는 사용자 기기의 시간대를 몰라서 날짜가 하루 어긋날 수 있다(서버가 UTC면 한국 오전 9시 전에는 전날). 해외에서는 휴대폰 시간대가 현지로 바뀌어 자연스럽게 현지 날짜가 된다 |
| 시각은 현지 시간대와 함께 저장한다. 기간은 시간대 없는 날짜로, 예정 시각은 날짜 없이 일차 + 현지 시:분으로, 실제 시각은 순간(UTC)으로 둔다 | 시간대 없이 저장하면 해외 여행의 시각이 한국 시간 기준으로 틀어진다. 예정 시각에 날짜를 넣지 않으면 기간이 없는 여행에도 넣을 수 있고, 여행 날짜를 옮기거나 다른 사람이 복사해도 그대로 맞는다(날짜는 시작일 + (일차 − 1)) |
| ID는 앱에서 UUID v7로 만든다. 공유 ID만 서버가 무작위로 만든다 | 장소와 구간이 서로를 ID로 가리켜도 서버 ID로 바꿔 끼울 필요가 없고, 같은 요청을 다시 보내도 중복으로 만들어지지 않는다. v7은 만든 시각 순서라 DB 인덱스에 유리하다. 공유 ID는 추측할 수 없어야 해서 서버가 만든다 |
| 이동 수단은 구간마다 여러 토막(수단 + 정류장 수 + 걸리는 시간)으로 담는다 | 실제 이동은 "지하철 2정류장 + 도보"처럼 갈아타는 경우가 많고, 정류장 수와 걸리는 시간이 동선을 이해하는 데 필요한 정보다 |
| 지도 전환은 화면이 아니라 **여행 단위**로 한다 | 지도를 움직일 때마다 지도가 바뀌면 화면이 깜빡이고 어색하다. 규칙: Stop이 모두 국내면 네이버, 하나라도 해외면 구글 |
| 지도와 장소 검색은 인터페이스로 분리한다 (`MapProvider`, `PlaceSearchProvider`) | 구글을 붙일 때 기존 코드를 갈아엎지 않기 위해서 |
| 구글은 MVP에서 빼고 2단계에서 Places, AI와 함께 넣는다 | AI 좌표 검증에 Places가 필요하다. 지도 표시만으로는 해외 검색이 안 돼서 반쪽짜리 경험이 된다 |
| **LLM이 준 좌표는 믿지 않는다** | 장소 이름만 받고 좌표는 Places API로 검증한다. 검색되지 않는 장소는 빼거나 표시한다 |
| AI 생성은 비동기 작업 + 푸시 알림으로 처리한다 | 생성이 수십 초 걸릴 수 있어 HTTP 타임아웃 위험이 있다 |
| AI는 서버를 거쳐서만 호출한다 | API 키 보호, 사용자별 횟수 제한, 같은 요청 캐싱, 비용 기록, 프롬프트 버전 관리를 서버에서 한다 |
| 로드밸런서는 **부하 테스트로 병목을 확인한 뒤** 도입한다 | 처음부터 붙이는 것보다 근거와 수치가 있는 개선 스토리가 된다 |
| 처음부터 stateless로 만든다 (JWT 인증, 파일은 S3) | 서버가 여러 대가 돼도 코드를 고치지 않게 하기 위해서 |
| 사용자가 올리는 여행 사진은 S3 Presigned URL로 업로드한다. 서버는 권한 확인과 URL 발급, 업로드 후 등록만 하고, 파일 데이터는 앱에서 S3로 바로 보낸다 | 사진은 크고 많아서 서버를 거치면 서버의 대역폭·메모리·시간을 크게 쓴다. 업로드 중에는 서버 인스턴스가 묶이고, 전송량도 두 배가 된다. 보안은 URL 유효 시간, 경로, 파일 형식·크기 제한으로 지킨다 |
| 사진은 앱에서 크기를 줄이고 위치 정보(EXIF)를 지운 뒤 올린다. 촬영 시각·좌표는 따로 저장하지 않는다 | 공유되는 사진 파일에 위치 정보를 남기지 않는다(개인정보). 촬영 시각·좌표를 쓰는 기능이 없으니 저장하지 않아 다루는 개인정보를 줄인다. 크기를 줄이면 업로드 시간과 S3 비용도 준다 |
| 여행·장소를 지우거나 회원 탈퇴하면 S3 사진도 지운다 | DB만 지우면 주인 없는 파일이 S3에 남아 비용이 들고, 개인정보도 남는다 |
| 핵심 결과물은 여행 동선 페이지와 여행 동선 이미지, 두 가지다 | 페이지는 앱 안에서 다시 보고 장소 정보를 확인하는 용도다. 이미지는 여행 전·중·후 모두 만들어 공유하는 핵심 기능이다 |
| 이미지는 저장하지 않고 항상 최신 여행 데이터로 다시 만든다. 이미지를 수정하려면 여행 데이터를 수정한다 | 여행을 수정하면 이미지도 자연스럽게 따라 바뀐다. 이미지 위에서 따로 편집하는 기능은 편집 상태를 별도로 저장해야 해서 범위가 커지므로 7단계 아이디어로 미룬다 |
| 이미지 내보내기 기술 검증을 0단계에서 먼저 한다 | Top 2 기능인데 네이티브 지도 스냅샷이라는 기술 위험이 있다. 위험한 것부터 확인한다 |
| 외부 지도 연결은 장소 이름과 좌표로 검색 링크를 만든다. placeId가 있으면 함께 쓴다 | MVP에는 Places 연동이 없어서 이름과 좌표만 있다. 정확한 링크 형식은 구현할 때 확인한다 |
| 공유받은 여행은 보기만 하고, 수정하려면 내 여행으로 복사한다 | 공동 편집은 멤버, 권한, 동시 수정 충돌 처리가 필요해서 범위가 크다. 복사 방식은 같은 목적(친구 동선을 받아 쓰기)을 훨씬 단순하게 해결한다 |
| 공유 화면에는 사진과 설명은 보여 주고 메모는 숨긴다 | 메모는 작성자의 개인 기록이다. 동선을 보여 주려는 목적에는 사진과 설명으로 충분하다 |
| 공유를 끄거나 링크를 새로 발급할 수 있다 | 링크는 한 번 퍼지면 회수할 수 없다. 잘못 보냈거나 더 이상 공개하고 싶지 않을 때 막을 수단이 필요하다 |
| 복사할 때 장소·구간·설명·예정 시각만 복사하고 사진과 메모는 뺀다 | 사진과 메모는 원본 작성자의 개인 기록이다. 사진 파일을 같이 쓰면 원본에서 지울 때 복사본이 깨지고, 따로 복제하면 S3 비용이 든다. 예정 시각은 시간 순서 자체가 동선 정보라서 복사한다 |
| 여행 중 화면은 오프라인에서도 볼 수 있게 한다 (2단계) | 해외에서는 데이터가 끊기는 일이 흔하다. 해외 지원과 함께 넣는다 |
| 여행 목록은 정사각형 카드 격자로 보여 준다. 휴대폰은 한 줄에 2개, 태블릿은 폭에 따라 3~4개다 | 사용자 결정. 한 화면에 여행이 더 많이 보이고, 카드에 나중에 동선 미리보기나 사진을 넣을 수 있다. 태블릿에서 2개면 카드가 지나치게 커진다 |
| 화면 글자는 Flutter gen-l10n(ARB 파일)으로 관리하고, 모델에는 글자를 두지 않는다. 지금은 한국어만 넣고 영어는 나중에 추가한다 | 영어를 넣을 때 ARB 파일만 추가하면 된다. 화면이 적은 지금 옮기는 비용이 가장 작다. Flutter 공식 도구라 build_runner가 필요 없다 |
| 디자인 시스템은 기본 값 → 의미 토큰 → 컴포넌트 테마 3단계로 만든다. 지금은 라이트 모드만 만들고, 토큰은 다크 모드를 고려해 정한다 | 화면과 내보내기 이미지가 같은 토큰을 써서 모양이 맞고, 색을 바꿀 때 한 곳만 고치면 된다. 다크 모드는 나중에 값만 더하면 된다 |
| 글꼴은 나눔스퀘어라운드(네이버, OFL)를 앱에 넣는다. 한글과 영문을 모두 지원하는 동글동글한 글꼴이다 | 서비스의 귀여운 분위기에 맞춘다. 굵기가 여러 개라 본문과 제목에 함께 쓰고, 한글 11,172자를 모두 담고 있다. 앱에 넣어야 내보낸 이미지가 기기마다 같은 글꼴로 나온다 |
| 주 색은 코랄(#FF6F61)이다 | 지도 바탕(물은 파랑, 공원은 초록) 위에서 동선이 잘 보이고, 둥근 글꼴의 귀여운 분위기와 어울린다. 파랑은 지도 앱에서 현재 위치를 뜻하므로 현재 위치 표시에 남겨 둔다 |
| 장소 설명은 사용자 작성 내용과 Places 정보를 나눠 표시한다 | 개인 기록과 객관적인 정보를 구분한다. Places 정보는 placeId로 조회하기 때문에 2단계부터 가능하다 |
| 지도 이미지는 앱에서 만든다 | 서버 렌더링보다 훨씬 간단하고 서버 비용이 없다 |
| GPS 기록은 "기록 시작 → 종료" 세션 방식이고 MVP에서 뺀다 | 상시 기록은 배터리, 개인정보, 스토어 심사 부담이 크다. 세션 방식도 백그라운드 위치 처리가 필요하다 |
| 여행 중 현재 위치 표시는 MVP에 넣는다 | GPS 기록과 다르게 "앱 사용 중" 권한만으로 충분하고 구현이 간단하다 |
| 서버는 NestJS를 쓴다 | 인증, 검증, 횟수 제한, 큐, Swagger가 공식 모듈로 있다. 구조가 정해져 있어 유지보수하기 쉽다 |
| Flutter 상태 관리는 Riverpod을 쓰고, 코드 생성은 쓰지 않는다 | 서버 데이터의 로딩·에러 상태와 여행별 상태를 기본으로 지원한다. 저장소·지도 구현을 바꿔 끼우기 쉬워서, 서버가 생기기 전에는 메모리 저장소로 화면을 만들고, 테스트에서는 지도를 가짜로 바꿀 수 있다. 코드 생성은 모델이 적은 지금은 얻는 것보다 부담(빌드 단계, 생성 파일)이 커서 필요해질 때 검토한다 |
| Flutter 라우팅은 go_router를 쓴다 | 3단계 공유 링크(딥링크) URL을 경로 표로 화면에 연결하고, 로그인 전에 링크를 열면 로그인 후 원래 화면으로 돌려보내는 처리를 한 곳(redirect)에서 한다. Flutter 팀이 관리하고 코드 생성이 필요 없다 |
| 테스트는 각 진영의 기본 도구(Jest, `flutter test`)를 쓰고, 단계별 완료 기준에 포함한다 | 가장 널리 쓰이는 방식이라 자료가 많고 설정이 적다. NestJS와 Flutter 모두 기본으로 설정돼 있다 |
| iOS는 MVP 이후, 맥이 있는 친구에게 부탁한다 | iOS 빌드와 디버깅에는 Xcode(macOS)가 필요하다 |

## 알아 둘 제약

- 네이버 지도는 해외 상세도가 낮고, 네이버 장소 검색은 사실상 국내 전용이다.
- 네이버 Directions API는 자동차 경로만 제공한다. 그래서 실제 경로 대신 직선·곡선으로 그린다.
- Firebase Dynamic Links는 2025년에 종료됐다. 앱 링크는 App Links / Universal Links로 직접 구현한다.
- 스토어 출시에 필요한 것
  - **개인정보처리방침:** 위치와 사진을 다루기 때문에 필수다. 실제로 쓸 때 수집 항목, 이용 목적, 보관 기간, 삭제 방법을 자세히 조사해서 작성한다.
  - **계정 삭제:** Google Play는 계정을 만드는 앱에 앱 안 삭제 기능과 웹 삭제 요청 경로를 요구한다.
  - **iOS:** Apple 개발자 계정(연 $99)이 필요하고 본인 명의로 만든다. 소셜 로그인이 있으면 Apple 로그인도 필요하다.
- AWS 비용에 주의한다.
  - ALB는 트래픽이 없어도 기본 요금이 나온다.
  - NAT Gateway는 비싸다.
  - Budget 알림을 처음부터 켜 둔다.
